# 评审改动

## 1. 先弄清意图与范围
- `git --no-pager status --short`、`git --no-pager diff --stat` 看改了哪些文件、改了多少。
- 读提交说明或任务描述：这次改动**想解决什么**？范围是否和意图匹配？夹带的无关改动要指出。

## 2. 逐处检查
| 方面 | 要问的问题 |
|---|---|
| 正确性 | 逻辑是否真的实现了意图？空值、空集合、边界值、并发、错误路径是否处理？ |
| 一致性 | 是否遵循周围代码的命名、风格、分层？是否重复造轮子（先 `grep` 看已有实现）？ |
| 安全 | 用户输入是否被信任？路径、命令、SQL、HTML 是否做了转义或校验？有无泄露密钥或敏感信息？ |
| 测试 | 新行为有没有测试？测试是否真能在行为坏掉时失败，而不只是跑通路径？ |
| 可维护性 | 命名是否准确？有没有不必要的复杂度？注释说的是「为什么」还是在重复代码？ |

## 3. 给出结论
- 按严重程度排序：必须改（会出错或不安全）、建议改、可选。
- 每条都指向具体文件与行，说明**问题是什么、为什么是问题、怎么改**；不确定的明确标注「不确定」，不要把猜测当事实。
- 没有发现问题就如实说没有，并说明检查了哪些方面。
