# 思考内容（Reasoning Content）

## 1. 这是什么

推理型模型在给出最终回答之前会先"思考"。不同服务商把这部分内容暴露给调用方的方式不同，大致有四种情形：

| 情形 | 表现 | 例子（以各服务商当前文档为准） |
|---|---|---|
| 完全隐藏 | 响应里没有思考内容，只在用量里体现推理 Token 数 | 部分闭源推理模型的聊天补全接口 |
| 明文返回 | 在消息上多出一个独立字段，例如 `reasoning_content` 或 `reasoning` | 部分开源推理模型及其兼容服务 |
| 带签名的块 | 思考以带签名的内容块返回，要求后续请求**原样回传** | 部分提供"扩展思考"的接口 |
| 加密的推理条目 | 返回不可读的加密载荷，需要原样带回以保持连续性 | 部分有状态推理接口 |

> 上表只描述类型，不保证任何具体服务商当前的行为。服务商的接口会变，**每个端点的行为必须通过配置声明并用集成测试验证**，不能写死在代码里。

现状代码对此一无所知：只读取 `choice.message.content` 和 `tool_calls`，思考内容被直接丢弃；构造请求时也不会回传。使用不返回思考内容的模型时没问题，换成会返回的模型就会出现三类问题：

1. 要求回传的服务商，在多轮工具调用中因为缺少思考块而报错或质量明显下降。
2. 明文思考内容被丢弃，用户看不到模型的推理过程，调试时失去最有价值的信息。
3. 反过来，**不该回传时回传了**也可能被拒绝或白白消耗 Token。

## 2. 要回答的四个问题

1. 怎么**取**：从响应里提取什么。
2. 怎么**存**：放进哪个数据结构，要不要持久化。
3. 要不要**回传**：下一次请求里怎么处理。
4. 怎么**用**：给谁看，能不能进入别的流程。

## 3. 取

网关按端点配置的 `reasoning_field` 提取明文思考内容：

```toml
[models.reasoning.endpoints.capabilities]
reasoning_field    = "reasoning_content"   # 响应消息上承载思考的字段名；空表示不返回
reasoning_passback = "never"               # never | tool_turns | opaque | all_when_tools，见 §5
thinking_with_tools = true                 # 为否时带工具的请求关闭思考，见 §5.2
```

- 官方 SDK 的响应模型允许额外字段，读取时用安全访问，缺失则为空，不抛异常。
- 带签名的块与加密条目属于**不透明载荷**，网关原样取出，保存为 `reasoning_state`，不解析、不修改、不截断。
- 同时记录推理 Token 数（若用量中提供），用于观测。

## 4. 存

`Message`（见 [状态模型 §1](../02_runtime/01_state_model.md)）增加两个字段：

```python
@dataclass(frozen=True, slots=True)
class Message:
    role: Role
    content: str
    tool_calls: tuple[ToolCall, ...] = ()
    tool_call_id: str | None = None
    name: str | None = None
    reasoning: str | None = None            # 明文思考，供展示与审计
    reasoning_state: Mapping | None = None  # 不透明载荷，仅用于回传；绝不展示、绝不改写
    produced_by: str | None = None          # 产生该消息的端点标识，用于判断能否回传
```

规则：

| 字段 | 规则 |
|---|---|
| `reasoning` | 可以截断以控制体积（存储上限默认 20000 字符），可以被前端展示 |
| `reasoning_state` | **逐字节原样保存**。签名一旦被改动就失效。大小可能可观，不做压缩以外的任何处理 |
| `produced_by` | 记录实际命中的端点名与模型。降级切换端点时它是判断依据 |

仅 `assistant` 消息会有这三个字段。

### 4.1 持久化

随检查点一起保存，因为续跑后继续同一个工具调用往返可能需要回传。但体积会增长，所以：

- `reasoning_state` 只保留**当前工具往返所需的部分**：自最近一条用户消息之后的助手消息。更早的在下次用户输入时丢弃，因为已知的服务商在新一轮用户输入之后都不要求回传更早的思考。
- `reasoning` 明文可以更早丢弃，只保留用于审计的截断版本在轨迹里，不留在状态中。

### 4.2 不进入的地方

| 位置 | 是否包含思考内容 | 原因 |
|---|---|---|
| 会话流水、会话记忆、压缩输入 | **否** | 思考内容是内部草稿，可能含不该沉淀的推测和被注入内容的复述 |
| 交付给用户的最终结论 | **否** | 交付是结论，不是草稿 |
| 对其他模型的上下文（子智能体、压缩器、评估阶段） | **否** | 草稿不应在模型之间传递，也可能被注入内容污染 |
| 任务内上下文折叠与压缩的输入 | 先丢弃 | 体积大且价值低 |

## 5. 回传策略

由端点配置的 `reasoning_passback` 决定：

| 取值 | 行为 | 适用 |
|---|---|---|
| `never`（默认） | 构造请求时丢弃所有 `reasoning` 与 `reasoning_state` | 不返回思考内容的模型；以及明确**不接受**回传的服务商 |
| `tool_turns` | 只在一个工具往返的尾部（最后一条用户消息之后的助手消息）回传明文思考 | 要求在工具调用往返中带回思考文本的服务商 |
| `opaque` | 对尾部助手消息回传 `reasoning_state` 原样载荷，且**必须原样、必须位于原来的位置** | 带签名块或加密条目的服务商 |
| `all_when_tools` | 请求带 `tools` 时，对**所有**历史助手消息回传明文思考；不带 `tools` 时不回传 | 要求"带工具必须回传全部历史思考，缺失即 400"的服务商，如 DeepSeek 的思考模式。**首版不启用**，原因见 §5.2 |

通用规则：

1. **只回传给产生它的同一模型。** `produced_by` 与本次请求的端点不一致时，丢弃回传内容。
2. **不修改。** 回传的载荷与取回时逐字节相同，且在消息中的顺序和位置不变。上下文折叠和压缩不得触碰这类消息的 `reasoning_state`；若必须折叠，整条一并处理，不留半条。
3. **缺失时优雅降级。** 配置了需要回传，但消息里没有载荷（例如从旧检查点恢复），则不回传并继续，不要因此失败。

### 5.2 一类需要特别对待的服务商：带工具必须回传全部

以 DeepSeek 为例（以官方文档为准，见 [DeepSeek §4](04_deepseek.md)）：思考模式下，**带 `tools` 的请求必须回传此前所有轮次的 `reasoning_content`，缺少会 400**；不带 `tools` 则回传可选且被忽略。

对这类服务商，只靠默认 `never` 是不够的，开着思考发工具请求会每次都失败。处理有两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| **A（首版采用）** | `thinking_with_tools = false`：带工具的请求显式关闭思考，不带工具的请求（规划、评估）照常思考 | 执行阶段没有自己的思考，但它本来只是把规划好的指令落成调用 |
| B | `all_when_tools`：持久化并回传每一条历史助手消息的思考内容 | 要把思考内容存进会话流水和检查点，与"思考内容不进入记忆"冲突；旧数据缺失时需要降级；体积和成本都增加 |

路线 A 同时避免了会话历史（只有问答，没有思考内容）与"所有历史轮次"要求的冲突。

### 5.1 为什么默认 `never`

回传错误的代价不对称。该回传而没回传：质量下降，或明确的错误提示，容易发现。不该回传而回传：可能被拒绝，也可能悄悄多算 Token。默认关闭，每个端点上线前做一次验证，再按需开启，是更安全的顺序。

## 6. 与降级的交互

降级链在同一次调用里切换端点，这对思考内容有直接影响：

```
端点 A（opaque 回传） ──失败──► 端点 B（never）
```

- A 产生的 `reasoning_state` 对 B 没有意义，甚至可能因格式非法被拒。B 的请求构造按 B 的策略处理：丢弃回传内容。
- **跨提供商的连续性无法保持。** 切到 B 之后，B 看不到 A 在这一轮之前的思考，只能基于可见的对话继续。这是降级的固有代价，写入网关文档，不尝试伪造。
- B 产生的新消息带 `produced_by = B`。如果下一次调用又回到 A，A 的回传检查会发现这条助手消息不是自己产生的，同样丢弃。
- 熔断导致整个任务实际在 B 上跑时，策略自然跟着 B。

## 7. 控制思考强度

请求里增加 `reasoning_effort`（`low`、`medium`、`high`，部分服务商另有 `max`），只发送给声明支持的端点。建议的默认：

| 用途 | 建议 |
|---|---|
| 规划、验收 | `medium` 或 `high` |
| 工具调度（执行阶段） | `low` |
| 记忆压缩、子智能体 | 不发送 |

思考强度直接影响延迟和推理 Token，应当成为可调参数，而不是跟着模型默认值走。

## 8. 预算

- 推理 Token 通常计入输出 Token，服务商返回的 `total_tokens` 已包含，物理预算不需要额外处理。
- 用量中的推理 Token 明细（若提供）记入 `Usage.reasoning_tokens`，用于观测和调优，不重复计费。
- 回传的思考内容会成为下一次请求的**输入 Token**。这在 `tool_turns` 与 `opaque` 下是真实成本，要计入上下文规模估算（见 [窗口与压缩 §3](../03_context/02_window_and_compaction.md)）。
- 端点不返回用量明细时无法区分，保持按总量计。

## 9. 展示

前端的调用检视器是思考内容最有价值的出口：

- 默认折叠，标注"模型思考过程（可能不完整）"。
- 只展示明文 `reasoning`；`reasoning_state` 永不展示。
- 展示前对金丝雀做脱敏。
- 提示用户：思考内容是模型的内部草稿，不是事实，也不是对用户的承诺。

事件载荷增加 `reasoning`（截断到事件限长）和 `reasoning_tokens`。

## 10. 安全

思考内容是模型输出，所有对模型输出的防护同样适用，另外有几条特别的：

1. **金丝雀检测必须覆盖思考内容。** 金丝雀指令明确写着"不得在思考中泄露"，而现状只检测回答文本和工具调用参数。推理模型可能在思考里复述系统提示词，包括金丝雀，所以泄露检测要扫描 `reasoning`。检测命中的处置与其他位置一致。
2. **思考内容不是可信信号。** 模型在思考里写"用户已经授权了这个操作"，不构成授权。权限判定只看动作本身。
3. **不作为决策依据。** 评估阶段、循环检测、预算守卫都不读取思考内容。
4. **不进入记忆**，见 §4.2，这同时阻断了通过思考内容向长期记忆投毒的通路。
5. **日志与轨迹可以保留截断的明文**用于排障，但要注意它可能含有用户数据与不可信内容的复述，保留期限按轨迹的策略处理。

## 12. 不变量

1. `reasoning_state` 一旦取出，到回传之前逐字节不变。
2. 思考内容只回传给产生它的同一模型。
3. 默认不回传；回传必须是端点上显式开启的配置。
4. 思考内容不进入会话记忆、交付结论、其他模型的上下文。
5. 金丝雀检测覆盖思考内容。
6. 缺少应回传的载荷时优雅降级，不使任务失败。

## 13. 测试要点

- 提取：有字段、无字段、字段为空、字段类型异常。
- 三种回传策略下构造出的请求内容；`never` 下请求里完全没有思考内容。
- 降级：A 产生的载荷不会被发给 B；回到 A 时不回传来自 B 的消息。
- 序列化：`reasoning_state` 往返字节级相等；旧检查点缺字段可加载。
- 裁剪：新一轮用户输入之后，旧的 `reasoning_state` 被丢弃，但尾部往返的保留。
- 折叠：折叠不改动带载荷的消息。
- 安全：思考内容里出现金丝雀会触发熔断；不出现在交付和记忆里；展示前已脱敏。
- 预算：回传开启后输入 Token 计量包含这部分。
- **按端点的集成测试**：对每个启用的端点，跑一个"多轮工具调用 + 思考"的用例，确认回传策略配置正确。这是配置验证，也是回归防线。

## 14. 待定

- 默认的 `reasoning_passback` 是否按已知服务商预置，还是一律 `never` 让用户显式开启。倾向后者，加一份"已验证端点清单"文档。
- 明文思考是否值得持久化到轨迹文件。体积大，但对调试价值高。可做成开关，默认只存截断版本。
- 前端是否实时流式展示思考内容。这要求网关支持流式调用，目前网关是非流式的，属于较大的改动，暂不纳入首版。
- 未来如果引入有状态的接口（服务端保存对话），回传策略需要重新设计，因为连续性由服务端保证，客户端只传引用。
