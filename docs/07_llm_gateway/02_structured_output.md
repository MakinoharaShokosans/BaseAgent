# 结构化输出

## 1. 要解决的问题

研究提炼、子智能体收尾、记忆压缩都需要模型输出结构化数据。主循环本身不用结构化输出（它读的是普通的助手消息与工具调用），旧实现的规划、评估场景随 [0006](../12_decisions/0006-pure-agent-loop.md) 取消，下文涉及它们的示例仅作机制说明。模型输出 JSON 不总是合法，也不总是符合预期的形状：

- 夹带 Markdown 围栏或前后解释文字。
- 缺字段、字段名漂移（`next_step` 还是 `action`）、类型错（字符串当列表）。
- 输出被长度截断，JSON 在中间断掉。

要让上层代码拿到的是**经过校验的强类型对象**，而不是满手 `dict.get()` 加兜底。

## 2. 现状

- 通过 `response_format={"type": "json_object"}` 请求 JSON 模式，并依赖提示词描述字段。
- `extract_json_object` 做宽松抽取：去掉代码围栏，失败则截取第一个 `{` 到最后一个 `}`。只保证抽出**一个字典**。
- 抽出后由各节点用 `.get()` 读字段。为了容忍字段名漂移，代码里堆了大量别名：规划阶段同时认 `next_step`、`action`、`next_action`；评估阶段把 `milestone_ok`、`is_completed`、`all_completed`、`status` 的多种取值都当作"通过/不通过"。
- 抽取失败的处理因节点而异：规划降级为纯文本指令，评估"按未达成处理"，研究与子智能体返回空报告。

这套做法能工作，但有三个问题：契约只存在于提示词和别名表里，没有任何地方给出权威定义；模型小幅偏离就会被静默吞掉，难以发现；失败路径各写各的，行为不一致。

## 3. 新版：三层保证

```
①请求层：让服务端尽量保证格式 ──► ②校验层：用 Pydantic 模型强校验 ──► ③修复层：失败时带着错误重试一次
```

### 3.1 请求层：按能力选择路径

网关根据端点能力声明选择，对调用方透明：

| 优先级 | 路径 | 适用 |
|---|---|---|
| 1 | `json_schema`（严格模式）：把 Pydantic 模型导出的 JSON Schema 交给服务端 | 端点声明 `json_schema = true` |
| 2 | `json_object` 模式加提示词里附 Schema | 端点声明 `json_object = true` |
| 3 | **以工具调用承载**：定义一个名为 `emit_result` 的工具，其参数就是 Schema，并强制模型调用它 | 端点支持工具调用但不支持 JSON 模式 |
| 4 | 纯提示词加宽松抽取 | 以上都不支持 |

路径 1 与 3 由服务端约束，比 2 和 4 可靠得多。路径 4 是保底，只用于本地小模型这类场景。

**DeepSeek 走路径 2**：文档只提供 `json_object` 模式，不提 `json_schema`。它的额外要求：提示词里必须出现 "json" 字样并最好附示例（网关构造请求时检查，缺失则补一句）；偶尔返回空内容，按瞬时故障重试；`max_tokens` 要足够大。路径 3 需要带 `tools`，在 DeepSeek 上只有关闭思考时才可用，见 [DeepSeek §5](04_deepseek.md)。

### 3.2 校验层：用模型定义契约

每个结构化场景定义一个 Pydantic 模型，作为该场景的**唯一契约**，提示词里的字段说明由模型导出，而不是手写两遍：

```python
class PlannerVerdict(BaseModel):
    thought: str
    next_step: str
    milestones: list[MilestoneSpec] = []
    milestone_updates: list[MilestoneUpdate] = []
    all_completed: bool = False
```

其他场景：`EvaluatorVerdict`、`ResearchRaw`、`SubagentRaw`、`CompactionResult`。

校验规则：

- **字段名不再接受别名。** 过渡期可以在模型里用 `validation_alias` 收口几个已知别名，但别名必须集中写在模型定义里，并带"计划删除"注释，不再散落在节点代码里。
- 类型严格但对常见的无害偏差宽容：`"true"` 可转布尔、单个字符串可包成列表。这些容忍规则同样写在模型里。
- 多余字段忽略，不报错。
- 数值与长度做边界约束（例如摘要不超过 300 字），超出时截断而不是拒绝。

### 3.3 修复层：带着错误重试一次

校验失败时，**不立刻降级**，而是把错误回给模型再试一次：

```
[原消息...]
assistant: <上次的输出>
user: 上一次输出未通过校验：缺少字段 `next_step`；`milestones[0].id` 应为整数。请只输出修正后的 JSON。
```

- 最多一次修复重试。多了只会放大 Token 和延迟。
- 修复重试**使用同一档位和同一端点**，不降级，因为这是格式问题而不是可用性问题。
- 两次都失败才进入降级路径。

## 4. 截断与空响应

| 情形 | 判定 | 处理 |
|---|---|---|
| `finish_reason == "length"` | 输出被截断，JSON 多半不完整 | **不要尝试修补残缺 JSON**。直接修复重试，提示"请缩短输出"；若仍截断，提高 `max_output_tokens` 重试一次 |
| 内容为空且无工具调用 | 空响应 | 当作瞬时故障重试 |
| `finish_reason == "content_filter"` | 被服务端过滤 | 不重试，作为失败向上报告，附原因 |

## 5. 降级路径

两次都失败后的行为必须**统一且显式**，不再由各节点自行决定。每个场景在契约里声明自己的降级方式：

| 场景 | 降级 | 原因 |
|---|---|---|
| ~~规划~~、~~评估~~ | 随 0006 取消（旧实现：规划按原文当指令，评估按未达成处理） | — |
| 研究 / 子智能体 | 空报告加告警 | 隔离区任何失败都不得透传原文 |
| 记忆压缩 | 保留旧记忆，水位线不推进 | 压缩是增强项 |

降级事件必须记录并计数，供评测统计各场景的格式失败率。这个指标比任何单元测试都更能说明提示词和模型是否匹配。

## 6. 抽取函数

`extract_json_object` 保留作为**第四层路径与修复前的预处理**，行为不变：去围栏、取首尾花括号之间的内容、只接受字典。补充两点：

- 当文本中出现多个顶层 JSON 对象时，**选择最后一个**还是第一个需要明确。模型在推理模型的思考泄漏到正文时，最终答案通常在最后。默认取最后一个完整对象，并写入测试。
- 提取出的 JSON 来自模型输出，而模型输出可能复述了不可信内容。它进入业务逻辑之前必须过 Pydantic 校验，不允许直接 `.get()` 后使用。

## 7. 安全

结构化输出本身是一条注入通路：不可信内容影响了模型，模型输出的 JSON 字段再被代码当作指令。防护靠**强类型与取值白名单**：

- 枚举字段用 `Literal`，例如里程碑状态、置信度。
- 路径、URL、版本号这类会被后续使用的字段，按各自契约再校验（见研究与子智能体的白名单）。
- 不把模型给出的任意字符串直接拼进命令或路径。

## 8. 提示词与契约的一致性

字段说明由 Pydantic 模型导出，避免提示词和代码各写一份而逐渐不同步。测试里加一项检查：每个提示词文件中出现的字段名，必须都存在于对应模型里；反之模型里的必填字段必须出现在提示词中。

## 9. 配置

| 项 | 默认 | 含义 |
|---|---|---|
| `structured.repair_retries` | 1 | 修复重试次数 |
| `structured.prefer_schema` | true | 端点支持时优先用 `json_schema` |
| `structured.on_truncate_raise_max_tokens` | true | 截断时修复重试把输出上限加倍（不超过端点上限） |

## 10. 不变量

1. 上层代码拿到的结构化结果一定是经过校验的 Pydantic 对象，或者明确的降级结果，二者可区分。
2. 字段别名只在模型定义里存在。
3. 截断的 JSON 不被修补后使用。
4. 修复重试最多一次，且不降级端点。
5. 每个场景的降级方式在契约里声明，行为统一。
6. 所有降级都有事件与计数。

## 11. 测试要点

- 各场景的合法输出、缺字段、类型错、别名、多余字段。
- 围栏、前后夹带文字、多个 JSON 对象、空响应、截断。
- 修复重试：第一次失败第二次成功；两次都失败走降级；修复请求里带上了校验错误。
- 路径选择：不同能力声明的端点走不同路径。
- 降级：评估失败按未达成；规划降级时事件被发出。
- 提示词与模型字段一致性检查。
- 注入：模型输出里的枚举字段取值不在白名单时被拒。

## 12. 待定

- 修复重试是否对规划这类昂贵的推理档调用也启用。成本上它是两次推理档调用，但失败时的替代方案是整步浪费。
- 是否按场景统计格式失败率，并在失败率异常时给出告警或自动切换到更严格的路径。
- 严格 `json_schema` 模式对 Schema 的限制（例如不支持某些关键字）较多，导出时需要一个"简化器"。

## 13. 实现细节（已落地于 `agent_runtime.llm`）

已实现：四条请求路径、抽取、校验、修复重试、截断与内容过滤、降级结果、计数与观测。**未实现**：各场景的契约模型与降级处置（随真实阶段落地）、提示词与模型字段一致性检查（§8）。

- **接口**：`await gateway.invoke_structured(LLMRequest(...), Model)` 返回 `Parsed[Model]`（`value`、`response`、各轮合计的 `usage`、`rounds`、`repaired`）或 `Degraded`（`reason`、`raw_text`、`problems`、`usage`、`rounds`）。二者是不同的类型，调用方用 `isinstance` / `match` 区分，不可能把降级结果当成已校验对象。网关错误（不可用、超时、请求被拒）照常抛出，不混进降级。结构化请求不能同时带调用方的工具（`ValueError`）。
- **路径按端点选**：降级到另一个端点时，路径随那个端点的能力重新选。顺序是 `json_schema`（`prefer_schema` 为假且有 `json_object` 时跳过）→ `json_object` → 工具承载 → 纯提示词。`LLMResponse.structured_path` 记录实际走的路径。
- **各路径的线上形态**：`json_schema` 发严格 Schema（见下）且提示词里不重复；`json_object` 与纯提示词把 Schema 追加到最前面的 system 消息（没有就在最前面补一条），文字里恒含 “JSON”，满足 DeepSeek 的要求；工具承载发名为 `emit_result` 的工具并强制 `tool_choice`，模型不调用而直接回文本时退回文本抽取。
- **严格 Schema 简化器**（§12 的待定项）：对象一律封闭（`additionalProperties: false`）且全部字段必填，去掉严格模式不接受的校验关键字（长度、范围、条数、`pattern`、`format`、`default`、`title`）。这些约束仍由 Pydantic 在收到输出后校验，不丢。字段名恰好叫 `title` 之类时不会被误删。
- **抽取**：整段是字典就直接用；否则扫描正文里的顶层对象，**取最后一个完整的**；整段是数组、对象在数组里，一律不接受。**到文末都没闭合（含字符串没写完）就整体返回空**，不会拿里面的片段凑数，也不修补。
- **校验错误描述**：只写路径与原因（`items[1].id：…`、“缺少字段 `next_step`”），**不回显输入值**，因为输入可能复述了不可信内容；最多 20 条，其余只报数量。
- **修复重试**：次数取 `repair_retries`（默认 1，可为 0）；每轮在原消息后追加“上一次输出 + 错误清单 + 请只输出修正后的 JSON”，多轮累积。修复请求通过 `LLMRequest.prefer_endpoint` **回到产生坏输出的端点**；该端点不可用时仍按顺序降级，因为可用性优先于固定端点。
- **截断**（`finish_reason == "length"`）：**不解析，即使内容看上去是完整 JSON**；提示“缩短输出”，`on_truncate_raise_max_tokens` 为真时输出上限加倍（构造请求时被端点上限封顶）。回显给模型的上一次输出超过 2000 字符就截掉，避免把超长输出再付一次费。再次截断则降级，`reason = "truncated"`。
- **内容过滤**：不重试，直接 `Degraded(reason="content_filter")`。**空响应**：属网关层的畸形响应，已在网关内重试一次，不算校验失败。
- **计数与观测**：`gateway.structured_counts` 是 `(purpose, outcome) → 次数`，`outcome` 为 `ok` / `repaired` / `degraded`，可直接算各场景的格式失败率；构造网关时传 `structured_observer` 可收到每次调用的 `StructuredRecord`（含路径、轮数、降级原因）。回调抛错只记日志，不影响调用。降级与修复事件如何进事件流，由真实阶段决定。
