# 事件与 SSE

事件是运行时对外说话的方式：前端的进度、工具调用、审批卡片、子智能体动态，全部来自事件流。本文定义事件的结构、谁来发、怎么传、怎么保存。事件名与载荷作为对外契约的完整定义见 [09_api](../09_api/)，本文约束的是运行时一侧。

## 1. 信封

每个事件都有统一的外层字段：

| 字段 | 说明 |
|---|---|
| `event` | 事件名，点分命名，如 `tool.call` |
| `task_id` | 所属任务 |
| `seq` | **任务内**单调递增的序号，由任务注册表在发出时分配 |
| `ts` | 发出时间戳（秒） |
| `v` | 事件模式版本，新增，见 §9 |

其余是事件自己的载荷。`seq` 是断线重连与顺序保证的依据，所以只有一个地方分配它。

## 2. 事件目录

| 分组 | 事件 | 发出者 | 时机 |
|---|---|---|---|
| 任务 | `task.started` | 任务运行器 | 开始执行 |
| | `task.waiting_for_approval` | 主循环 | 挂起检查点提交后 |
| | `task.approved` / `task.rejected` | API 层 | 收到审批决策 |
| | `task.finished` | 任务运行器 | 终态，含状态、原因、回合数、Token（统计值）、交付 |
| | `task.error` | 任务运行器 | 不可恢复异常或游标缺口 |
| 回合 | `model.reply` | 主循环 | 模型回复追加之后 |
| | `plan.updated` | 主循环 | `update_plan` 执行之后 |
| | `turn.finished` | 主循环 | 每个回合结束提交之后 |
| | `context.compacted` | 主循环 | 任务内压缩提交之后；只带数字（并入步数、压缩前 Token、摘要长度、`llm`/`mechanical`），不含摘要正文 |
| 工具 | `tool.call` | 主循环 | 回复提交后，每个调用一条 |
| | `tool.result` | 主循环 | 结果追加提交后，每条观察值一条 |
| 模型 | `llm.call` | **LLM 网关** | 每次模型调用（含重试与降级） |
| 研究 | `websearch.started` / `.round` / `.finished` | 研究运行器 | |
| 子智能体 | `subagent.started` / `.step` / `.tool` / `.blocked` / `.finished` | 子智能体运行器 | |
| 传输 | `heartbeat` | SSE 层 | 空闲时周期发送，**不带 `seq`** |

## 3. 谁来发：三条规则

1. **主循环在提交检查点之后发事件**，不是之前。事件反映的是已经落盘的事实，客户端看到的进度不会比可恢复的进度更远，见 [主循环 §3](../02_runtime/02_main_loop.md)。
2. **`llm.call` 由网关发**，调用方不再各自复制，见 [网关 §12](../07_llm_gateway/01_gateway.md)。
3. **叶子工具（子智能体、研究）通过任务级事件总线发**，总线负责限长与容错，见下。

## 4. 事件总线

每个任务一个，是父级把"对外回调"推送给叶子的通道（和授权窗口同一种手法）：

- 任务开始前绑定本轮的回调，结束时解绑，避免闭包持有已完成的注册表。
- 叶子调用 `emit(event)`，总线加上 `task_id`，把 `summary`、`excerpt`、`detail`、`reason` 四类字段**强制限长到 300 字符**并压平空白。这是隔离承诺的一部分：可观测性不得成为原始内容外泄的通道。
- **永不向上抛异常**：回调失败只记录警告。事件发不出去，任务继续。
- 没有绑定回调时（非流式运行）只写调试日志，不缓冲、不阻塞。
- 总线**自己不缓冲**：重放由注册表的缓冲负责，两处各存一份会漂移。

## 5. 传输：SSE

```
GET /tasks/{task_id}/stream          Accept: text/event-stream
Last-Event-ID: <seq>            （重连时）
```

- 先重放缓冲里 `seq` 大于游标的事件，再接实时。
- 空闲时每 `sse_heartbeat_sec`（默认 15）发一次 `heartbeat`，防止代理断连。
- **游标缺口**：客户端的 `Last-Event-ID` 早于缓冲最旧的事件时，发一条 `task.error` 带 `code=STREAM_GAP` 后结束，要求客户端改用任务快照与时间线重新同步。
- **背压**：每个订阅者有独立的有界队列。队列满时**丢弃该事件并记录警告**，不阻塞任务执行。

### 5.1 现状的缺口

1. **订阅者不知道自己丢了事件。** 丢弃是静默的。客户端必须自己检测 `seq` 不连续，并主动重连。新版在服务端也应该做：队列满后，下一条成功投递的事件前补一条 `stream.dropped`（带丢失区间），或者直接断开该订阅者，让它带着游标重连。
2. **缓冲只在内存。** 事件、任务句柄都在进程内。重启后任务列表、事件历史都没了，只剩检查点与轨迹文件。
3. **缓冲单位是条数，不是字节。** 默认 1000 条。`llm.call` 事件携带**完整的消息体和系统提示词**，一条可达数百 KB，1000 条里混入几十条就占用几十兆内存。
4. **`llm.call` 被当作事件缓冲的一部分来查询。** 调用检视接口直接从缓冲里筛 `llm.call`，缓冲滚动后早期的调用就查不到了。

## 6. 新版设计：持久化事件

事件应当有一份持久副本，让时间线、检视器、重启后的恢复都不依赖进程内存。

```sql
CREATE TABLE task_events (
    task_id  TEXT NOT NULL,
    seq      INTEGER NOT NULL,
    ts       REAL NOT NULL,
    event    TEXT NOT NULL,
    payload  TEXT NOT NULL,          -- 不含大块内容的 JSON
    blob_ref TEXT,                   -- 大块内容（如 llm.call 的完整消息体）的文件引用
    PRIMARY KEY (task_id, seq)
);
```

- 事件由注册表在分配 `seq` 时**同步写入**（批量提交，容忍丢失最后几条）；这是旁路，写入失败只告警。
- 内存缓冲只作为最近事件的热缓存，用于 SSE 重放加速；冷数据从表里读。游标缺口因此基本消失：除非事件已按保留策略被清理。
- **大块内容外置**：`llm.call` 的完整 `messages`、`tools`、响应放到 `storage/traces/{task_id}/llm/{seq}.json`，事件里只带摘要（档位、模型、Token、耗时、消息条数、`blob_ref`）。前端的检视器按需拉取。这同时解决内存占用和查询滚动的问题。
- 任务重启或续跑后，`seq` 接着已有的最大值继续，不重置。

### 6.1 保留策略（设计，未实现）

目前没有任何清理：事件、轨迹、产物都一直累积，需要时手动清理数据目录。下面是打算做的策略；之前配置里的 `storage.retention` 没有被任何代码读取，已删除，实现时再加回。

| 数据 | 默认保留 |
|---|---|
| 事件表 | 最近 30 天或最近 200 个任务 |
| `llm.call` 大块内容 | 最近 7 天或最近 50 个任务，总量上限（如 1 GB） |
| 轨迹文件 | 与事件表一致 |

清理打算在启动时和每天一次执行，策略写进配置。

## 7. 内容与脱敏

事件会被前端展示，也可能被截图、分享。规则：

| 内容 | 处理 |
|---|---|
| 工具入参 | 进入 `tool.call`。需要经统一脱敏函数：疑似密钥的字段（名含 `key`、`token`、`secret`、`password`）与高熵长字符串替换为 `[REDACTED]` |
| 工具观察值 | `tool.result` 只带前 500 字符；完整内容在产物里 |
| 命令 | 保留（用户需要看到执行了什么），但同样过脱敏 |
| `llm.call` | 含系统提示词（含金丝雀）和全部观察值。**仅本机回环**，在大块内容里展示前对金丝雀脱敏；文档注明不要分享该数据 |
| 思考内容 | 截断，并在展示前对金丝雀脱敏，见 [思考内容 §9](../07_llm_gateway/03_reasoning_content.md) |
| 页面正文 | **不进入事件**（研究隔离承诺） |

## 8. 顺序与一致性

- 同一任务的事件由**单个发出点**（注册表）分配 `seq`，天然全序。
- 子智能体的并发步骤可能交错，但各自的 `subagent.*` 事件带 `depth` 与 `role`，前端据此归组。
- 事件顺序保证：对同一个检查点提交，其对应的事件在提交之后出现；`task.finished` 总是最后一个带 `seq` 的事件。
- 事件可能重复（崩溃后重做某个回合会再次发出）。消费者按 `(task_id, seq)` 去重，但崩溃重做会产生**新的 `seq`**，对应的是新发生的事件。前端以回合序号显示进度，而不是依赖事件条数。

## 9. 版本

事件载荷会演进。信封里加 `v`（整数，从 1 开始）。规则：

- 新增字段不升版本；消费者必须忽略未知字段。
- 删除或改变字段含义必须升版本，并在 09_api 中记录。
- 前端遇到更高版本的事件，退化为只显示事件名与时间，不报错。

## 10. 不变量

1. 发事件永远不会让任务失败。
2. 事件不携带原始网页正文。
3. 摘要类字段限长，不依赖发出者自觉。
4. `seq` 在任务内单调递增且只有一个分配点。
5. 事件在对应检查点提交之后发出。
6. 大块内容不占用事件缓冲。
7. 工具入参与命令在进入事件前经脱敏。

## 11. 测试要点

- 总线：未绑定时静默；回调抛异常被吞掉；摘要字段被限长；缺少 `event` 字段的事件被忽略。
- SSE：先重放再实时；游标缺口返回 `STREAM_GAP`；心跳不带 `seq`；慢消费者不阻塞任务，且被通知丢失。
- 顺序：并发子智能体事件的 `seq` 全序；`task.finished` 最后。
- 持久化：重启后能读到历史事件；`seq` 续接；清理策略生效。
- 脱敏：密钥样的参数被替换；`llm.call` 外置，缓冲里只有摘要。
- 大小：混入大量 `llm.call` 后内存占用有界。
- 版本：未知字段被忽略；更高版本的事件前端不报错。

## 12. 待定

- 是否在服务端对 `llm.call` 做采样（只保留每 N 次或失败的完整内容），以降低存储。
- 事件表是否放入与检查点相同的 SQLite 文件。放在一起便于一致性，但写入频率差异大，会让检查点库变忙；倾向单独的文件。
- 是否提供 WebSocket 以支持前端向服务端发控制消息。目前审批与取消都走普通 HTTP，SSE 已足够。

## 13. 实现状态

- **脱敏**（`observability.Redactor`）：键名含 `key/token/secret/password/authorization/cookie`（配置可改）的值、已知密钥形态、命令里的凭据片段（`Authorization:` 头、`--password`/`--token` 等选项、`FOO_TOKEN=` 赋值、URL 里的 `user:pass@`）、不含斜杠的高熵长串（≥32 字符且熵 ≥4.3、至少两类字符；纯十六进制哈希不会被误伤）、以及精确的金丝雀。**局限**：`-p <值>` 这类歧义写法没有处理（`mkdir -p` 会被误伤），属已知取舍。
- **事件库**（`EventStore`）：单独的 SQLite 文件，WAL，0600；`prune(older_than, keep_tasks)` 按任务整体清理。清理策略的**定时执行**尚未接上。
- **事件中心**（`EventHub`）：见 [事件契约 §12](../09_api/02_events_contract.md)。热缓存按任务数与条数双重有界，有订阅者的任务不会被淘汰；序号接着事件库里的最大值走，续跑与重启都不重置。
- **`llm.call`**：网关的调用记录是同步回调，`LlmCallEvents` 用当前任务的上下文变量（`core.current_task_id`，由任务运行器设置）认出任务并后台发出；`drain` 在收尾前等它们发完。**未做**：外置完整提示词与响应（调用记录里没有正文）、研究与子智能体事件、保留策略的定时清理。
