# 审批与安全相关的界面

安全机制再严密，最后一道门是人。审批界面如果让人看不清自己在批准什么，或者把"批准"做成一个随手一点的按钮，前面所有防护都会在这里失效。本文约束这些界面的设计。

## 1. 审批卡片

### 1.1 现状

`HitlApprovalCard` 展示：动作类型徽标、越级原因、待执行命令（代码块）、三个操作（批准本次、当前会话免审、拒绝并填写理由）。拒绝时有一个文本输入，默认理由为"用户在交互审批卡片中拒绝执行该高危操作"。

结构是对的，几处需要改进。

### 1.2 必须展示的信息

| 信息 | 来源 | 要求 |
|---|---|---|
| 动作类型与所需级别 | `action_type`、`required_level`、`current_level` | 用人话，如"网络外联：需要全权限，当前为工作区写入" |
| **完整命令** | `command` | **不截断**；过长时可折叠但默认展开前几行并显示总长度；保留空白与换行；等宽字体 |
| 判定原因 | `reason` | |
| 同批其他动作 | `related_actions`、`escalation_count` | 一批里有多个越级动作时明确说明"本次批准将同时放行这 N 项"，列出全部而不是只显示第一个 |
| 发起方 | 主 Agent 或哪个子智能体 | 子智能体不会发起审批，此项为将来预留 |

现状 `related_actions` 最多只带 4 项，`escalation_count` 是总数，二者要一起显示，如"另有 3 项未列出"。

### 1.3 防误操作

1. **批准按钮不是默认焦点**。键盘回车不应直接批准。默认焦点放在"拒绝"或中性的"查看详情"上。
2. **"当前会话免审"必须有解释与二次确认。** 它的含义是：本会话内**完全相同的命令**不再询问。界面要显示将被加入白名单的具体内容，而不是一句抽象的"免审"。可用一个折叠的说明加确认勾选。
3. **危险命令的强提示。** 命中 `rm -rf`、`sudo`、`git push --force`、管道到 shell（`| sh`、`| bash`）等模式时，卡片用更强的视觉提示，并要求逐字确认或延迟启用批准按钮（例如 1.5 秒）。
4. **防点击劫持与重复提交。** 提交决策后立即禁用按钮并显示"已提交"，等待服务端确认；服务端对重复提交返回 409，界面据此显示当前状态而不是报错。
5. **审批过期或已被处理。** 若卡片展示期间任务状态已变（被取消、被另一个窗口处理），收到状态事件后卡片自动失效并说明原因。

### 1.4 拒绝

- 拒绝理由有常用选项（"只在本地生成补丁，不要推送"、"不要联网"、"换一种方式"），也可自由输入。
- 理由会作为观察值**回给模型**，界面要提示这一点，让用户知道写什么会被模型读到。
- 默认理由不要冒充用户的话。若用户没有输入，使用中性的"用户拒绝了该操作"。

### 1.5 提交内容

必须带上 `approval_id`，与卡片展示的请求绑定，见 [09_api/01 §3](../09_api/01_endpoints.md)。服务端在不匹配时返回 409，界面据此刷新卡片。

## 2. 权限基线选择

`Composer` 允许在提交任务时选择权限基线，并把值作为 `permission_level` 发送。

| 级别 | 界面表达 |
|---|---|
| `read_only` | "只读：只能查看，不会修改任何文件" |
| `workspace_write`（默认） | "工作区读写：可在工作区内修改文件、构建、测试；联网、安装、推送需要确认" |
| `full_permissions` | "完全权限：**不再请求确认**，包括联网、安装、推送、系统级命令" |

选择 `full_permissions` 时：

1. 弹出明确的确认对话框，说明"此任务中所有操作将自动执行，不再询问"，需要用户主动确认，不是默认记住；
2. 请求里带 `confirm_full_permissions: true`；
3. 任务运行期间，状态栏与头部**持续显示**当前基线，用警示色，不能让用户忘了自己开了什么；
4. 不要把 `full_permissions` 作为会话级或全局的默认值被记住，每次任务都要重新确认。

## 3. 来源与信任的可视化

用户需要能区分"这是 Agent 自己说的"、"这是工具返回的"、"这是外部不可信内容"：

| 内容 | 展示 |
|---|---|
| 助手消息 | 普通气泡 |
| 工具观察值 | 带工具名的折叠块，默认只显示摘要 |
| 不可信来源的观察值（MCP、研究报告） | 明显标记，如"外部内容（不可信）"，用不同的底色，不与助手气泡混淆 |
| 子智能体结论 | 标明"未经验证"的条目；已验证条目显示引用，可点击查看来源 |
| 研究报告 | 来源链接以文本显示，点击前显示域名，新窗口打开并带 `rel="noopener noreferrer"` |
| 越级被拒（子智能体） | 单独的一条提示，说明哪个动作因权限被拒 |

## 4. 渲染来自 Agent 的内容

所有来自模型、工具、网页的文本都**视为不可信**，渲染时：

- Markdown 使用 `react-markdown`，**不启用原始 HTML**（不使用 `rehype-raw`），不使用 `dangerouslySetInnerHTML`。当前实现符合，需要用测试固定下来。
- 链接：只允许 `http`、`https`、`mailto`；其他协议（`javascript:`、`data:`）不渲染为可点击；外链带 `rel="noopener noreferrer"` 与 `target="_blank"`。
- 图片：默认**不自动加载外部图片**。外部图片可以用来向攻击者的服务器传送信息（URL 里带数据）。需要时由用户点击后加载，或只允许同源与数据 URL。
- 代码块：只做语法高亮，不执行。
- 超长内容：虚拟滚动或折叠，避免一个巨大的观察值卡死页面。
- 终端控制字符与 ANSI 转义序列：显示前剥离或转换，避免界面被污染。

## 5. 敏感信息的展示

- **金丝雀**：在任何展示模型原始内容的位置（调用检视器、思考内容）前做脱敏替换。
- **密钥**：展示命令与参数前经过与服务端相同的脱敏规则（服务端已脱敏，前端再做一道，防御纵深）。
- **本地路径**：绝对路径会暴露用户名与目录结构。界面里可以只显示相对工作区的路径，完整路径放在悬停提示里。
- 截图与分享：调用检视器顶部提示"此视图包含完整提示词与工具输出，请勿分享"。

## 6. 破坏性操作的确认

| 操作 | 确认方式 |
|---|---|
| 删除工作区 | 说明会级联删除全部会话、记忆、轨迹、产物；要求输入工作区名称确认 |
| 删除会话 | 说明会删除流水与记忆 |
| 删除记忆条目 | 简单确认，可撤销一小段时间 |
| 保存文件（用户在画布里编辑） | 带冲突检测（`base_hash`），冲突时显示差异并让用户选择 |
| 取消任务 | 说明状态会停在最近的检查点，之后可以续跑 |

## 7. 不变量

1. 审批卡片展示完整命令，不截断到无法判断。
2. 批准不是默认焦点，重复点击不会重复提交。
3. `full_permissions` 每次任务都要显式确认，且持续可见。
4. 不可信内容在界面上与可信内容有明确区分。
5. 来自 Agent 的文本从不被当作 HTML 或可执行内容渲染。
6. 敏感信息展示前脱敏。
7. 破坏性操作都有与影响相称的确认。

## 8. 测试要点

- 审批卡片：完整命令展示；批准按钮非默认焦点；危险模式的延迟启用；提交后禁用；`approval_id` 随请求发送；409 后卡片刷新；任务状态变化后卡片失效。
- 权限选择：选择 `full_permissions` 弹确认；请求体带确认字段；持续警示。
- 渲染：含 `<script>`、`onerror`、`javascript:` 链接、外部图片、ANSI 转义的 Markdown；断言没有可执行内容、外部图片不自动加载。
- 脱敏：金丝雀和疑似密钥在检视器里被替换。
- 破坏性操作：确认流程、名称输入校验。
- 可访问性：审批卡片可用键盘完整操作，对比度满足要求，屏幕阅读器能读出命令与风险级别。

## 9. 待定

- 是否在审批卡片里提供"风险解释"：用一句话说明这条命令会做什么（由规则生成，不由模型生成，避免模型替自己的请求背书）。
- 是否支持对一批越级动作逐项选择（见 [审批 §10](../02_runtime/04_approval.md)）。
- 桌面通知：任务挂起等待审批时，用户可能不在页面前。是否提供系统通知，以及通知里是否包含命令（隐私）。
