# 窗口与压缩

对话变长之后，上下文必须被控制。这里有**两个完全不同的时间尺度**，现有实现只处理了其中一个。

| 尺度 | 对象 | 现状 |
|---|---|---|
| **会话级** | 跨任务的用户与 Agent 对话流水 | 已实现：高低水位线加滚动压缩 |
| **任务级** | 单个任务内的 `messages`（工具调用往返） | **没有窗口，没有压缩**，只有观察值裁剪 |

本文先描述会话级机制，再指出任务级缺口并给出新版设计。

## 1. 会话级：水位线与滚动压缩

### 1.1 数据

会话里只保存**人机对话流水**：每个任务贡献两条记录，用户的任务目标与 Agent 的最终交付。工具调用往返不入流水，它们只存在于任务内的 `messages` 和轨迹文件里。

```
session_turns(id, session_id, role[user|assistant], content, token_count, timestamp)
session_memories(session_id, compacted_until_turn_id, summary, confirmed_facts, failed_attempts, last_action_target)
```

`compacted_until_turn_id` 是**水位线指针**：此 id 及之前的轮次已经被提炼进 `summary`，不再作为原文进入上下文。活跃轮次就是 id 大于水位线的那些。

### 1.2 任务开始：装入

```
活跃轮次 = id > compacted_until_turn_id 的全部轮次
若活跃轮次数 < active_window_turns：改取最近 N 轮（保底）
```

装入后转成消息序列，再把本次任务目标作为最新的 user 消息接在末尾，符合模型预训练时的对话时序。已压缩的 `summary`、`confirmed_facts`、`failed_attempts` 通过系统提示词的会话记忆层带入，见 [提示词装配](03_prompt_assembly.md)。

保底取最近 N 轮时，这几轮可能已经被压缩进了摘要，原文与摘要会有轻微重复。可以接受，换来的是摘要质量不佳时也不至于完全失去最近的上下文。

### 1.3 任务结束：写入与触发

任务收尾时：

1. 计量用户目标与交付的 Token，写入流水。
2. 更新 `last_action_target`（上一轮核心修改的实体，如文件、符号）。
3. 汇总活跃（未压缩）轮次的 Token 总和。
4. 若总和 ≥ `session_token_limit × compaction_high_watermark`，触发压缩。

默认值：上限 32000，高水位 80%，即 **25600** 触发；压缩目标 40%，即切出约 **12800** Token。

### 1.4 切片：对话对齐

不允许在一条消息中间截断。算法：

1. 从最旧的轮次开始累加 Token。
2. 当累计值达到目标，并且**当前这条是 assistant 回复**时，在此处截断。这样切出的永远是完整的"用户问加 Agent 答"。
3. 如果没有找到这样的位置（例如所有 assistant 回复都出现在目标之后），退而求其次：取列表中最后一个 assistant 节点，但**至少留出最后一条**。
4. 总共只有一条消息时不截断。

结果是 `(待压缩, 保留)` 两段。保留的部分留在活跃窗口，水位线推进到待压缩段的最后一条的 id。

由于对齐到 assistant 边界，实际切出量会略高于目标。

### 1.5 提炼

由快速档模型执行，输入是**既有记忆**加**待压缩的轮次**，输出严格 JSON：

```json
{ "summary": "更新后的整体背景与进展，300 字以内",
  "confirmed_facts": ["…"],
  "failed_attempts": [{"action": "…", "failure_reason": "…", "conclusion": "…"}] }
```

提示词的纪律：

- 去粗取精，只保留技术决策、验证属实的事实、已完成的结论。
- **已有的关键事实不被推翻就必须继承。**
- 失败的尝试必须提炼进 `failed_attempts`，防止重复踩坑。
- 合并语义重复的事实。

合并规则：

| 字段 | 合并方式 |
|---|---|
| `summary` | **替换**为模型给出的新摘要；模型未给时保留旧摘要 |
| `confirmed_facts` | 旧事实 **追加** 新事实，再按字符串去重 |
| `failed_attempts` | 旧条目 **追加** 新条目，解析失败的条目跳过 |

### 1.5.1 新版：压缩任务记录，而不是压缩散文

现状压缩的是原始对话文本，让快速档模型从"用户目标 + 交付散文"里捞事实。质量不稳、成本高，多轮之后还会漂移。新版改为：**任务交付时就产出一条结构化的任务记录，会话压缩只合并这些记录**。

任务收尾时系统手里本来就有结构化信息（计划完成情况、笔记里的事实与失败尝试、`last_action_target`、终止原因、产物句柄），把它们固化成一条约 200 到 400 字的记录：

```
TaskRecord
  task_id、时间
  goal            用户目标原话（截断）
  outcome         成功 / 部分 / 失败 / 被终止
  touched         改动的文件与符号
  decisions       关键决定，标明是用户定的还是 Agent 定的
  facts           本任务新确认的事实，每条带来源与验证状态
  failed_attempts 失败的做法与原因
  open_items      遗留问题
  artifacts       产物句柄
```

会话流水里仍保留用户目标与交付原文（供界面展示和审计），**任务记录是给模型用的压缩载体**。原始记录和流水都不删除，水位线只决定哪些进入摘要，摘要是缓存而不是唯一副本。

**保留与丢弃：**

| 保留 | 丢弃 |
|---|---|
| 用户的决定、约束、偏好 | 寒暄、过程叙述 |
| 文件与符号引用 | 工具原始输出（只留产物句柄） |
| 已验证的事实 | 未验证的推测 |
| 失败的做法与原因 | 重复的结论 |
| 未解决的问题 | 思考内容 |

原则是**引用优于内容**：记"改了 `loop/driver.py` 的 `drive`，详见产物 X"，不记那段代码。

**提炼的约束：**

1. **摘要不滚雪球。** 结构化字段（事实、失败尝试）单独存、带上限，超限时由模型**整体重新整合**，不是只追加。叙述性摘要限 300 字，每次基于"旧摘要 + 新任务记录"重写。每合并若干次，从原始任务记录**全量重建一次**以纠正累积误差。
2. **每条事实带出处。** 要求给出来源任务 id，系统校验 id 真实存在；没有出处的事实丢弃。
3. **不允许静默丢失。** 压缩后做差异检查：旧事实若不在新输出里，模型必须把它列入 `superseded` 并给出理由，否则系统原样补回。
4. **带验证状态进入记忆。** 来自子智能体报告或研究报告的结论，只有 `verified` 的才可能成为"已确认事实"，并保留来源标记；未验证的只记入 `open_items` 或不记。见 [记忆 §5.3](04_memory.md)。
5. **输出受约束。** 严格 JSON 加 Pydantic 校验，失败带错误修复重试一次，仍失败则保留旧记忆；禁止输出命令、指令、凭据；输出过注入扫描，命中的条目丢弃。
6. **走网关。** 快速档，温度 0，通过 `LLMGateway` 调用，享有降级与重试，见 [网关](../07_llm_gateway/01_gateway.md)。

**触发方式：**

- **滞回**：到 80% 触发，一次压到约 40%，少次大批量，也最小化缓存失效，见 §3.2.1。
- **异步**：先提交任务终态、发出完成事件，再在后台压缩。压缩期间同一会话的新任务读到旧水位，压缩完成后再生效。
- **边界对齐**：仍只在完整的"问加答"处切，至少留最近 3 轮原文。
- **手动触发**：用户在输入台点“压缩记忆”，`SessionCompactor.compact_now`。不看水位线与退避（这是用户明确的意图），切片目标取到够不着，因此除保留的最近几条外全部并入；失败照旧回退为上一版记忆。没有可并入的轮次且没有待合并的近期新增时不调用模型。

**质量评估：** 做一个探针评测。对一批历史会话，压缩前后各问一组事实性问题（"之前决定用什么方案""哪个做法失败过，为什么"），统计压缩后的召回率。看摘要读起来是否通顺没有这个有用。

### 1.6 降级

压缩是增强项，**绝不阻断主流程**：模型超时、返回非 JSON、解析异常，一律回退为上一版记忆，只记录警告。此时水位线**不推进**，下一个任务会再次尝试，待压缩的轮次会越积越多。新版加指数退避与连续失败提示，见 §2 第 4 项。

## 2. 会话级机制的已知问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **事实与失败尝试只追加不收敛**。提示词要求"合并去重"，代码却是旧列表加新列表再做字符串去重，语义重复无法消除 | 列表无限增长，而它们每次都完整进入系统提示词，占用越来越多的窗口 | 设上限（如事实 50 条、失败 30 条），超出时让压缩器重新整合整份列表而不是只追加；或按时间与引用频次淘汰 |
| 2 | **压缩器绕过了模型网关**。它直接取快速档的第一个端点调用，不走降级链、不走重试 | 首选端点不可用时压缩直接失败，且没有退避 | 统一走 `LLMGateway`，见 [07_llm_gateway](../07_llm_gateway/) |
| 3 | **压缩同步发生在任务收尾阶段**，在发出任务结束事件之前被等待 | 任务结果已经产出，但用户要多等一次模型调用才看到"完成" | 先提交任务终态并发出事件，再异步压缩；压缩期间对同一会话的新任务需等待或读到旧水位 |
| 4 | **压缩失败后无退避** | 每个任务都重试，反复失败反复耗时 | 失败计数与指数退避，连续失败后提示用户 |
| 5 | **`compaction_trigger_turns`（轮数保底触发）配置存在但没有被任何代码读取** | 配置误导 | 要么实现，要么删除 |
| 6 | **只按 Token 触发，不考虑轮数**。很多很短的轮次永远不会触发压缩 | 影响有限 | 同上，决定是否实现轮数保底 |

## 3. 任务级：缺口与新版设计

### 3.1 现状

任务内的 `messages` 从装入的会话轮次开始，每一步追加 assistant 的工具调用与对应的 tool 观察值。**每次模型调用都把全部 `messages` 连同系统提示词一起发送**，没有窗口、没有裁剪、没有压缩。当前唯一的控制手段是：

- 单条观察值裁剪（≤ 1500 Token 的摘要）。
- 步数上限 25（旧设计；目标设计已取消）。

但这个上界并不小：25 步里每步若有 1500 Token 的观察值再加模型自身输出，累计上万 Token 并不稀奇，还要乘上会话历史、系统提示词与记忆层。上下文窗口有限的模型（或成本敏感的场景）会先于步数上限触顶，全量重发还使每次调用的成本随步数近似平方增长。

> 目标设计（[0006](../12_decisions/0006-pure-agent-loop.md)）取消了步数上限与预算，任务可以任意长，所以**窗口治理不再有任何兜底**：折叠与压缩是长任务能跑下去的唯一手段，不能省。

### 3.2 新版设计：三级渐进

遵循"先便宜、后昂贵"的原则，只有前一级不够用时才进入下一级。

**级别 1 观察值裁剪（已有）。** 见 [观察值治理](01_observation_governance.md)。

**级别 2 旧观察值折叠（新增，无模型调用）。**
当装配后的提示词 Token 超过 `task_context_soft_limit`（例如模型窗口的 60%）时，把**较早步骤**的 tool 消息正文替换成一行存根：

```
[已折叠] bash: pytest -x（退出码 1，共 842 行）→ 完整输出见产物 obs_step_4_bash
```

规则：

- **只改 tool 消息的正文，不动结构。** assistant 的 `tool_calls` 与 tool 消息仍成对存在，原子对不变量不被破坏。
- 最近 K 步（默认 3）不折叠，保证模型正在处理的证据完整。
- 折叠是**对装配结果的视图操作**，不改写 `state.messages`。原文留在状态里，检查点与轨迹不丢，只是不再每次都发给模型。
- 折叠后的存根必须带产物句柄，配合 `read_artifact` 随时取回，见 [观察值治理 §6.1](01_observation_governance.md)。
- **可重放的读取不需要产物句柄**：`view_file`、`grep`、`list_dir`、`read_artifact` 的结果靠同样的调用就能取回，折叠只留一行“需要时用同样的参数重新调用”的存根（配置 `fold_reproducible_tools`）。读取类工具的结果不再被观察值治理器截成头尾（`passthrough_tools`），所以它们本来就没有产物，折叠是它们唯一的瘦身途径。

**级别 3 任务内压缩（新增，调用快速档模型）。**
折叠之后仍超过 `task_context_hard_limit`（例如窗口的 80%）时，把**最旧的若干个完整步骤**（assistant 调用加其 tool 响应组成的原子组）交给快速档模型提炼，产出写成一条摘要消息（持久化方式见 §3.3），并在装配视图里用它替换这些步骤。同样不改写 `state.messages`。

压缩单位必须是**原子组**，不能切开一次工具调用与其结果。

### 3.2.1 与前缀缓存的关系：成批、低频

折叠与压缩都会改写**已经发送过**的内容，所以每次都是一次**已知的缓存失效**：被改动的位置之后，整段缓存重新计算。这决定了它们的触发方式：

- **到阈值才做，一次做完。** 不要每步折叠一条。达到软阈值时，把"除最近 K 步之外"的全部旧观察值**一次性**折叠，使规模回落到低水位（例如窗口的 40%），之后很长一段时间不再触发。
- **滞回**：触发线（60% / 80%）与回落线（约 40%）之间留出空间，避免在阈值附近反复触发。
- 折叠后的存根内容必须**确定**（只用工具名、退出码、行数、句柄，不含时间戳），同一内容多次折叠结果相同。
- 会话级压缩同理：80% 触发，一次压到约 40%，见 §1.3。每次压缩使会话记忆段及其后的近期问答缓存失效一次，所以压缩要少而大。
- 任务收尾沉淀的事实**不**立即并入会话摘要，先进入"近期新增"，压缩时才并入，见 [提示词装配 §3.6](03_prompt_assembly.md)，避免每个任务结束都让摘要变化。

跨任务时没有这个问题：会话流水只存问答，上一个任务的工具往返不会出现在下一个请求里，新请求只有末尾是新的。

### 3.3 继承摘要与任务内进展分开

- **继承来的历史摘要**只存在于任务启动时冻结的提示词资产里，任务内只读，状态里没有对应字段，所以任何任务内写入都覆盖不到它。
- **任务内的进展**由草稿承担：计划、`facts`、`failed_attempts`（[计划与草稿](../02_runtime/05_plan_and_scratch.md)），它们在请求尾部回显，不进继承摘要。
- 级别 3 的任务内压缩产出一条摘要消息替换若干旧步骤。为使装配视图可复现，这条摘要随状态持久化：`stream_summary`（摘要正文）与 `stream_cut`（目标消息之后有多少条往返已并入摘要），状态版本升到 4，见 [状态模型](../02_runtime/01_state_model.md)。`state.messages` 不动，所以检查点、轨迹和续跑看到的仍是完整 transcript。

### 3.4 上下文规模

新增一个**上下文规模**度量，用于触发级别 2 与级别 3：每次装配后按分词函数估算提示词 Token，与模型窗口比较。这个度量只做局部决策，用服务商返回的用量校准偏差，不对应任何额度，也不会终止任务。

## 4. 配置项

已有：

| 项 | 默认 | 含义 |
|---|---|---|
| `session_token_limit` | 32000 | 会话活跃对话 Token 上限 |
| `compaction_high_watermark` | 0.80 | 触发线 |
| `compaction_ratio` | 0.40 | 目标压缩量 |
| `active_window_turns` | 3 | 保底保留的最少轮数 |
| `compaction_trigger_turns` | 8 | 目前无效，见 §2 第 5 条 |

新增（任务级）：

| 项 | 建议默认 | 含义 |
|---|---|---|
| `task_context_window_tokens` | 按模型配置 | 任务内提示词的窗口大小 |
| `task_context_soft_ratio` | 0.60 | 触发折叠 |
| `task_context_soft_tokens` | 100000（按成本调） | 触发折叠的**绝对上限**，实际触发线 = `min(窗口 × soft_ratio, soft_tokens)`。窗口很大（如 1M）时比例阈值几乎不会触发，成本却随上下文增长，所以必须有绝对上限，见 [DeepSeek §7](../07_llm_gateway/04_deepseek.md) |
| `task_context_hard_tokens` | 160000（按成本调） | 触发任务内压缩的绝对上限，同理取 `min` |
| `task_context_hard_ratio` | 0.80 | 触发任务内压缩 |
| `task_fold_keep_recent_steps` | 3 | 最近多少步保持完整（折叠与任务内压缩共用） |
| `compaction_enabled` | true | 是否做级别 3 任务内压缩 |
| `compaction_summary_chars` / `compaction_input_chars` | 4000 / 60000 | 摘要的字符上限 / 送去总结的旧步骤的字符上限 |
| `fold_reproducible_tools` | `view_file` `grep` `list_dir` `read_artifact` | 结果靠同样的调用能取回的工具：折叠只留一行存根 |
| `memory_max_facts` / `memory_max_failed_attempts` | 50 / 30 | 记忆列表上限 |

## 5. 不变量

1. 压缩与折叠永远不切开原子组：assistant 的 `tool_calls` 与其全部 tool 响应要么都在，要么都被同一操作处理。
2. 会话级压缩只在完整的"问加答"边界截断。
3. 压缩失败不阻断任务，不丢失既有记忆，水位线不推进。
4. 折叠与任务内压缩只作用于装配视图，不改写持久化的状态。
5. 任务目标永久锚定，不被折叠或压缩。
6. 折叠遵循 [上下文继承](05_inheritance.md) 的分类：可重放的存根无需句柄，不可重放的必须有句柄。
7. 水位线单调不减。

## 6. 测试要点

- 切片：恰好对齐、全是 user 消息、只有一轮、assistant 都在目标之后；切出量略高于目标但不越界。
- 压缩：模型返回非 JSON、返回缺字段、超时；失败后水位线不变；事实去重。
- 水位线：连续多个任务后单调推进，活跃轮次始终在上限附近。
- 折叠：原子对完整；最近 K 步不受影响；存根含产物句柄；折叠前后检查点内容一致。
- 任务内压缩：以原子组为单位；摘要持久化后重放得到同一视图；不覆盖继承摘要。
- 记忆上限：超出后触发整合，列表长度受控。

## 8. 实现状态

会话级机制已实现（`agent_runtime.memory.compactor`、`slicing`、`merge`）；任务级的级别 2 折叠已实现（§8.1），级别 3 的任务内压缩已实现（§8.2）。

- **触发与切片**：活跃轮次（水位线之后）的 Token 之和达到 `token_limit × high_watermark` 触发；切片在累计量达到 `token_limit × compaction_ratio` 之后的**第一个 assistant 回复之后**截断，够不到目标时取允许范围内最后一个 assistant 节点，无论如何至少留下最近 `active_window_turns` 条（按流水条数计，不是问答对数）。属性测试：任意输入下切出的都是以 assistant 结尾的前缀，且剩余不少于保底。真实配置下每次切出约 12800 Token，与“一次压到约 40%”一致；任务本身很大时（单任务就占上限的大半），一次压缩可能压不到低水位，下一个任务会继续。
- **提炼约束（§1.5.1）已落地**：没有真实出处（任务 id 不在被压缩的轮次或既有条目里）的新事实丢弃（`require_provenance`）；提炼结果过注入样态扫描，命中的事实、失败尝试和摘要丢弃；旧事实或旧失败尝试没被列入 `superseded` 就原样补回（不静默丢失）；超过 `max_facts` / `max_failed_attempts` 淘汰最旧的；摘要截断到 `summary_max_chars`，模型没给就保留旧摘要。压缩器提炼出的**新**事实一律标 `untrusted`、来源 `compressor`；既有条目保留原有出处与信任。
- **“近期新增”并入**：压缩时把既有记忆与近期新增一并交给提炼器，结果合并后近期新增清空；**提炼期间新沉淀的不会丢**（合并时只清掉快照里那些）。近期新增超限时可以强制压缩，此时没有轮次可切，水位线不动，只做并入。
- **失败与退避（§2 第 3、4 项）**：提炼器返回 `None`（网关降级）、抛异常，都回退为上一版记忆，水位线不推进，失败计数加一，下一次允许重试的时间按 `compaction_backoff_sec` 推迟（序列用完后沿用最后一项），退避期内不再调用提炼器；成功后计数清零。取消不被吞。同一会话同一时刻只有一次压缩，不同会话互不阻塞。
- **走网关**：`GatewayExtractor` 用快速档与结构化输出（`purpose="compactor"`），输入里的对话与记忆都包在信封里（正文中的信封标签会被破坏）。**未做**：温度 0（`LLMRequest` 还没有这个字段）、重建（每合并若干次从原始记录全量重建一次）、探针评测、任务记录 `TaskRecord`（§1.5.1 前半）、`compaction_trigger_turns`（配置已删除，不实现）。

### 8.1 级别 2：旧观察值折叠（已实现）

`context.fold.fold_stream`，由 `PromptAssembler(fold=FoldPolicy(...))` 在装配时对**任务内往返**（最新需求之后的消息）应用；历史、记忆、数据层与尾部不动，`state.messages` 不被改写，视图的消息条数与配对不变（只换 tool 消息的正文）。`runtime.fold_policy_from_settings(settings, context_window)` 取 `min(窗口 × soft_ratio, soft_tokens)` 为触发线；新增配置 `context.task.fold_exempt_tools`（默认 `["load_skill"]`）。

- **折叠决定是消息序列的纯函数，不写状态。** 从头重放：每条消息之后，若“流之外各段的规模 + 可见的任务内消息”达到触发线，就把除最近 `fold_keep_recent_steps` 步之外的旧观察值**一次性**折叠；之后只有可见规模再次触到触发线才会再折叠。所以折叠是成批的（40 步的流只发生少数几次，有测试）、单调的（折叠过的永远折叠，有测试与 Hypothesis 性质），两次折叠之间上一次的请求（除尾部）是这一次的前缀，缓存可以命中。重放的代价是每次装配 O(消息数)，可以接受；缺点是触发判断用的是装配器的计数函数，与网关的真实用量不严格一致，只做局部决策。
- **“一步”** = 带 `tool_calls` 的 assistant 消息及其响应；规划者的纯文本指令不算一步。最近 K 步永远完整。
- **存根**：`[已折叠] <工具>: <调用摘要>（N 行，M 字符）→ 完整输出见产物 artifact://<id>，可用 read_artifact 取回`。调用摘要取 `command` 或参数的排序 JSON，压成一行并截到 80 字符；句柄取内容里**最后一个** `artifact://`（治理器追加的那个，不是正文里引用的别的产物）。内容只由工具名、参数、行数、字符数与句柄决定，没有时间戳。
- **不折叠**：没有离线副本（内容里没有句柄）的观察值——折叠会让它永远取不回，而它们本来就不超过观察值阈值；豁免工具（`load_skill`）；存根并不比原文短的。**例外**：`fold_reproducible_tools` 里的工具没有句柄也折叠，存根是 `[已折叠] view_file: {...}（N 行，M 字符）→ 需要时用同样的参数重新调用 view_file`——它们的读取结果可以靠同样的调用取回。
- **未做**：存根里的退出码（`ToolResult` 的退出码不在消息里，只能从原文推）；assistant 消息里超大的工具参数不折叠；按窗口大小以外的信号（如真实用量）触发；回落到低水位（现在是“折叠到只剩最近 K 步”，K 与触发线的比值决定每批折多少）。

### 8.2 级别 3：任务内压缩（已实现）

`context.task_compaction.TaskCompactor`，由循环内核在**每次调模型之前**问一次（`TaskRuntime.compact`）。

- **触发**：装配后的规模达到 `min(窗口 × hard_ratio, hard_tokens)`（窗口取所有已装配端点里最小的，用户换模型也安全）；折叠先于它起作用，所以走到这里说明折叠之后仍然太大。自动压缩至少要并入 2 个新步骤，免得每个回合都花一次模型调用。
- **只改视图**：结果是状态的两个字段 `stream_summary`、`stream_cut`；装配器在 `<user_task>` 之后放一条 `<task_summary trust="untrusted">`，并丢掉目标之后的前 `stream_cut` 条消息。`state.messages` 不动。摘要出自对不可信观察值的总结，所以仍标不可信（系统提示词的数据隔离协议里列了 `<task_summary>`）。
- **切点**：总是落在带 `tool_calls` 的 assistant 消息之前，不会切开调用与结果；最近 `fold_keep_recent_steps` 步保留原文。再次压缩时旧摘要作为输入，已并入的步骤不再重复送去总结。
- **提交点**：压缩后立即提交检查点，再发 `context.compacted` 事件（只带数字，不含摘要正文），与其他事件同样“先提交后发”。
- **总结**：快速档、结构化输出（`purpose="task_compaction"`，提示词 `prompts/task_compactor.md`）：记录读过什么、得出什么结论、改了什么、试过什么失败；计划与笔记已另外保存，不重复；旧摘要未被推翻的内容保留。运行时层注入总结函数（`context` 层不依赖 `llm`）。
- **压缩不让任务失败**：模型不可用、超时（120 秒）、输出为空都退回机械的调用清单（带一行说明，前端用警告色显示），窗口照样变小；压缩器抛异常，内核记日志后继续不压缩。
- **溢出恢复**：模型报告上下文溢出（`LLMBadRequest.context_overflow`）时，强制压缩一次（只留最近 1 步）再重试；重试仍溢出、或已经没有可压的步骤，就原样抛出。
- **未做**：摘要里的事实回写到会话记忆；按真实用量触发；对摘要质量的自动评测。

- **异步压缩（§2 第 3 项）未做**：`MemoryFlow.finish` 目前同步等待压缩。之前的 `compaction_async` 配置项没有被任何代码读取，已删除；要做时再加回。
