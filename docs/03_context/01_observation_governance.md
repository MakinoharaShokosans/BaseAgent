# 观察值治理

## 1. 要解决的问题

工具输出是上下文膨胀的头号来源：`cat` 一个大文件、一次完整编译、一轮压力测试，动辄上万行。直接放进上下文会带来三个后果：

- **Token 爆炸**：每一轮模型调用都要把整段输出再发送一遍。
- **中间迷失**：模型对超长文本中间部分的利用率很低，关键报错反而被埋掉。
- **窗口被无谓占用**：每轮重发的成本随步数累积，窗口很快见底。

治理原则：**上下文里放摘要，全文放磁盘，摘要里带上取回全文的办法。**

## 2. 两道关口

观察值要经过两道独立的裁剪，分属不同进程，职责不同：

| 关口 | 位置 | 处理对象 | 手段 |
|---|---|---|---|
| ① Shell 蒸馏 | `bash_shell` sidecar | 命令的 stdout / stderr | 流式捕获，有界缓冲，结构化嗅探，关键字过滤，全量日志落盘，见 [沙箱 §3.5](../05_security/02_shell_sandbox.md) |
| ② 观察值裁剪器 | Agent 进程，工具后处理内 | **所有工具**的返回内容 | Token 阈值触发，结构化轮廓或头尾关键行，全文落盘 |

①只管 `bash`，因为它要在输出还在流式产生时就控制内存。②是所有工具的统一兜底，包括 `view_file`、MCP 工具、子智能体报告。

> 两道关口叠加时，`bash` 的输出可能被截两次：先被 sidecar 蒸馏成约 50 行，再被裁剪器按 Token 判断。通常第二道不会触发，因为第一道已经把量压下来了。但两套"省略提示"的格式不同，模型看到的句柄也不同，见 §6。

## 3. 裁剪器

### 3.1 触发

```
原始观察值 ──► 计量 Token ──► ≤ 阈值？ ──是──► 原样返回，不产生磁盘副作用
                                │
                                否
                                ▼
                       全文落盘 ──► 生成摘要 ──► 摘要 + 句柄
```

| 配置 | 默认 | 含义 |
|---|---|---|
| `max_observation_tokens` | 1500 | 超过此值才裁剪 |
| `observation_head_lines` | 20 | 文本摘要保留的头部行数 |
| `observation_tail_lines` | 30 | 文本摘要保留的尾部行数 |

**读取类工具不按头尾截断。** `passthrough_tools`（`view_file`、`grep`、`list_dir`、`read_artifact`、`websearch`）自带行数与翻页上限，把读到的文件截成“头 20 行 + 尾 30 行”会让模型看不到它明明读了的中间部分（实测 300 行的 `view_file` 从 4658 Token 被砍到 1194）。它们的单条结果允许到 `passthrough_max_tokens`（默认 12000），超过才摘要加落盘；这类结果的瘦身交给折叠（可重放的读取折成一行存根，见 [窗口与压缩 §3.2](02_window_and_compaction.md)）。

计量使用全系统统一的分词函数，见 [记忆 §7](04_memory.md)，裁剪器本身通过注入的计数函数工作，不直接依赖分词库，便于测试替换。

### 3.2 摘要策略

按输出形态选择，**结构化优先**：

**JSON（以 `{` 或 `[` 开头且能解析）**：不做字符截断，因为截断会把语法切碎。生成**结构轮廓**，仍是合法 JSON：

- 递归到最大深度 3，更深处只保留类型提示。
- 数组只展开前 5 项，其余用"其余 N 项省略"代替。
- 字符串标量最多预览 120 字符；嵌套容器用 `<list len=N>`、`<object keys=[…]>` 表示。

**纯文本**：头部 N 行 + 尾部 M 行；中间部分如果命中错误关键字，再保留最多 30 行关键行。

关键字（不区分大小写）：`error`、`fatal`、`warning`、`failed`、`undefined reference`、`segmentation fault`、`traceback`、`exception`、`assert`。

没有任何命中时，中间只留一行"中间省略 N 行"。总行数不超过 `head + tail` 时不蒸馏，原样返回。

### 3.3 落盘与句柄

- 路径：`{artifacts_dir}/{task_id}/obs_step_{step_id}_{tool_name}.log`
- 写入在线程池中执行，不阻塞事件循环。
- **落盘失败不中断任务**：降级为只保留摘要，并记录错误。此时没有句柄。
- 摘要末尾附一行：`[完整输出已离线保存: artifact://obs_step_3_bash]`
- 句柄登记进 `AgentState.artifacts`（`artifact_id -> 磁盘绝对路径`），HTTP 层据此向前端展示产物。

### 3.4 豁免

`load_skill` 返回的是技能 SOP，截断会让流程指引残缺。它的阈值放宽为 8 倍（默认约 12000 Token），仍有上限，防止超大的恶意技能撑爆上下文。豁免名单是一个构造参数，其他同类工具可以加入。

## 4. Token 口径

裁剪器不改变工具的真实输出，只改变放进上下文的那一份。本地分词只用于**裁剪触发**和**压缩触发**这类局部决策，不对应任何额度；用量统计以服务商返回为准，由网关记录。

## 5. 失败与降级

| 情形 | 处理 |
|---|---|
| 分词库不可用 | 退回字符粗算，`len(text) // 2`，只告警一次 |
| JSON 解析失败 | 退回文本蒸馏 |
| 落盘失败 | 只留摘要，记录错误，任务继续 |
| 空输出 | 原样返回 |

## 6. 已发现的缺口：句柄无法被模型取回

系统提示词要求模型"引用大段输出时说明其产物句柄"，摘要里也写着 `artifact://…`，但**没有任何工具能解析这个句柄**：

- `view_file` 只能读工作区内的文件，而产物落在 Agent 工程自己的 `storage/artifacts/` 下，在工作区之外，会被路径校验拒绝。
- 句柄只是一个标识（`obs_step_3_bash`），不是路径，`bash cat` 也无从下手。
- 只有 HTTP 的产物接口能列出它们，但那是给前端用的。

后果：被裁剪的部分对模型来说**永久丢失**。如果关键信息恰好在被省略的中间部分，模型只能重新执行命令。

### 6.1 新版设计：`read_artifact` 工具

新增一个只读、分页、限定范围的内置工具：

```
read_artifact(artifact_id, start_line?, end_line?, grep?)
```

- 只能读取**当前任务**登记在 `state.artifacts` 里的产物，不接受路径。
- 与 `view_file` 同样返回带行号的片段，单次最多 400 行，超出提示继续翻页。
- 可选 `grep` 参数做正则过滤，避免为了找一行报错而翻几十页。
- 权限级别 `read_only`，加入 `read_only_tools`。
- 信任级别 `trusted`。产物内容来自本任务自己的工具输出，其信任级沿用原工具：若原输出来自不可信工具，读取时同样加不可信信封，所以登记产物时需记录原工具的信任级。

同时统一两套句柄：sidecar 的原始日志路径和裁剪器的 `artifact://` 句柄，登记进同一张 `artifacts` 表，摘要里只出现 `artifact_id`。

## 6.2 实现状态

`context.observation`：`ObservationGovernor.govern`、`ObservationStore`（落盘在线程池，失败不抛）。与上文的差异：行数不超过 `head + tail` 但每行巨长时，按长度再封顶每行（至少 80 字符），否则几行 base64 会整条放行；同一步内句柄重名时加 `_2`、`_3`；工具名与任务 id 净化后才进路径。`read_artifact` 已实现（[内置工具 §4、§11](../04_tools/02_builtin_tools.md)）：与 `view_file` 同样分页，支持 `grep`；`tool_runner` 把 `state.artifacts` 整体推给任务绑定对象，并把工具自带的产物（sidecar 的命令日志）登记进同一张表，被截断时在观察值里追加句柄，两套句柄由此合一。产物的来源信任由句柄推出（`obs_step_{n}_{工具}`、`step_{n}_{工具}`），认不出的按不可信。登记表不存信任级，所以这是“从命名推断”而不是记录，换成显式记录需要扩展 `artifacts` 的结构，待定。**未做**：产物清理。

## 7. 不变量

1. 未超阈值的观察值原样进入上下文，不产生磁盘副作用。
2. 合法 JSON 的摘要仍是合法 JSON，永不做字符级截断。
3. 全文落盘失败不影响任务继续。
4. 裁剪发生在信封包裹之前，信封警示语不会被截掉。
5. 豁免工具有硬上限。
6. 产物只能写入 `artifacts_dir/{task_id}/` 下。

## 8. 测试要点

- 阈值边界：恰好等于、略大于阈值。
- JSON：嵌套深度、大数组、超长字符串标量、非法 JSON 退回文本。
- 文本：行数不足时不蒸馏；有无关键字命中；关键字行上限。
- 落盘失败（目录不可写）时仍返回摘要且无句柄。
- 豁免工具在 8 倍阈值内完整保留，超出后仍被裁剪。
- `read_artifact`：越权访问其他任务的产物被拒；分页；`grep`；原工具为不可信时带信封。
- 任务结束后产物目录的保留与清理策略（见待定）。

## 9. 待定

- 产物的生命周期：任务结束后保留多久，是否按总量上限清理。目前没有清理机制，长期运行会持续占用磁盘。
- 是否对 JSON 轮廓的深度和数组展开数做配置化。
- `view_file` 自身的 400 行限制与裁剪器阈值是两套口径，是否统一。
