# 提示词装配

## 1. 要解决的问题

"模型此刻看到了什么"必须**可复现、可检视**。如果各处自己拼提示词，就无法保证口径一致，也无法解释"为什么模型忘了刚才的结论"。因此装配集中在一个只读组件里：

- **纯装配**：不写状态、不调用模型、不落盘。
- 同一份状态，永远装配出同一份提示词。
- `/sessions/{id}/context` 检视接口直接复用它，用户看到的就是模型看到的。

第二个目标是**前缀缓存友好**：模型服务通常按请求前缀缓存，前缀逐字节相同的部分不重复计算，更快也更便宜。所以排序的总原则是：**越稳定、越长久不变的越靠前；越易变的越靠后；新内容只追加，不回头改。**

## 2. 装配结构

```
┌ 全局静态 ───────────────────────────────────── 跨工作区、跨会话共享，永不压缩
│  0. 系统层       角色、安全与数据隔离协议、工作法、金丝雀（第一条 system 消息）
│  1. 工具 Schema  API 的 tools 字段，会话内固定
├ 工作区范围 ─────────────────────────────────── 同一工作区的所有会话共享
│  2. 技能清单     常驻，见 §3.5
│  3. 项目规则槽   opt-in，见 §4
│  4. 工作区常量   名称、cwd、描述
│  5. 工作区记忆   用户画像、工程准则、架构定论、全局避坑
├ 会话范围 ───────────────────────────────────── 同一会话的所有任务共享
│  6. 会话记忆     会话摘要、已并入的事实与失败尝试，慢变，可压缩
│  7. 近期问答     历史的用户目标与交付，追加式
├ 任务范围 ───────────────────────────────────── 任务开始时确定，任务内冻结
│  8. 本任务数据   环境自检、近期新增事实（见 §3.6）
│  9. 最新需求     用户刚发来的话（当前任务目标）
├ 10. 任务内往返 ──────────────────────────────── 追加式
│     assistant 的工具调用 · 工具观察值 · 研究报告 · 子智能体报告 · 技能 SOP
└ 11. 草稿回显 ────────────────────────────────── 每次调用的尾部，临时，不入历史
```

| 序 | 层 | 内容 | 变化频率 | 可压缩 | 信任 |
|---|---|---|---|---|---|
| 0 | 系统层 | 角色、安全与数据隔离协议、工作法、金丝雀 | 随版本（金丝雀随安装，可配置为随会话） | 否 | 可信 |
| 1 | 工具 Schema | 当前主工具集的函数定义 | 会话内应当固定 | 否 | 可信 |
| 2 | 技能清单 | 名称、一句话描述、触发词、来源与告警标记 | 工作区启用技能时 | 否 | 带信封，含不可信来源标记 |
| 3 | 项目规则槽 | 工作区的规则文件 | 随工作区，极少变 | 否 | 带信封，见 §4 |
| 4 | 工作区常量 | 工作区名称、cwd、描述 | 随工作区 | 否 | 可信 |
| 5 | 工作区记忆 | 画像、准则、架构、全局避坑 | 偶尔，用户手动改 | 整合 | 用户输入可信，其余带来源 |
| 6 | 会话记忆 | 摘要与已并入的事实、失败尝试 | **仅在压缩时变** | 是 | 带来源与信任标记 |
| 7 | 近期问答 | 历史的目标与交付 | 每任务追加两条 | 是 | 助手交付不可信度同其来源 |
| 8 | 本任务数据 | 环境自检、近期新增事实 | 每任务，任务内冻结 | 否 | 视来源，带信封 |
| 9 | 最新需求 | 当前任务目标，作为 user 消息 | 每任务 | 否 | 用户输入，可信 |
| 10 | 任务内往返 | `messages` 中本任务产生的部分 | 每步追加 | 折叠 / 压缩 | 工具与子智能体内容带信封 |
| 11 | 草稿回显 | 任务目标一行、计划、本任务笔记、证据提醒 | 每次调用 | 否 | 模型自己的陈述，不作指令 |

### 2.1 消息角色映射

| 段 | 请求中的位置与角色 |
|---|---|
| 0 | 第一条 `system` 消息，**也是唯一的 `system` 消息** |
| 1 | `tools` 字段，由服务端聊天模板渲染进提示词 |
| 2、3、4、5 | **`user` 角色的独立消息**，各带 `source`、`trust` 属性的信封。技能清单、项目规则、工作区记忆都可能受不可信内容影响，放在 `user` 侧可以降低它们被当作系统权威的风险；工作区常量可信，同样放 `user` 侧 |
| 6 | `user` 角色的独立消息，带信封 |
| 7 | 交替的 `user` / `assistant` 消息，历史的目标与交付 |
| 8 | `user` 角色的独立消息，带信封，任务开始时确定 |
| 9 | `user` 消息：当前任务目标 |
| 10 | `assistant`（含 `tool_calls`）与 `tool` 消息，追加式 |
| 11 | 请求最末尾的临时 `user` 消息，不入历史 |

多条连续的 `user` 消息是合法的，但个别端点要求角色严格交替。网关的能力声明里加 `merge_consecutive_user`，为真时把相邻 `user` 消息合并成一条，段之间用分隔标题隔开，合并后的字节序必须仍然稳定。

关于第 10 段：**研究报告、工具观察值、子智能体报告、技能 SOP 不是单独的一层**，它们是任务内往返里的 `tool` 消息，追加在最新需求之后，各自带信任信封。一个任务进行到中途时，最后一条消息通常是工具结果，而不是用户的话。第 9 段"最新需求"指的是**任务开始的那一刻**，随往返增长它会被推向上下文中间，所以第 11 段的第一行会重复一次任务目标，见 §2.2。

### 2.2 为什么这样排

排序同时服从两条：KV 缓存和注意力。

**KV 缓存（前缀匹配）：按共享范围从宽到窄。** 缓存命中要求前缀逐字节一致，任何一个字节不同，其后全部失效。所以让被最多请求共享的内容最先出现：全局 → 工作区 → 会话 → 任务 → 回合。结果是：

- 同一会话的下一个任务，复用到近期问答为止；
- 同一工作区新开一个会话，复用到工作区记忆为止；
- 同一任务的下一回合，复用整个已发送的前缀。

由此有两个具体后果：

- **系统层只含全局静态内容。** 工作区名、cwd 只要进了系统消息，系统层之后的一切就失去跨工作区共享的可能，所以拆到工作区范围里。金丝雀必须留在系统层（它防御的就是系统层被抽取，见 §3.2），因此它的作用域取安装级而不是会话级，让系统层保持全局静态。
- **系统层排在工具 Schema 之前。** 系统层只随版本变，工具集却可能因 MCP 或授权变化。系统层在前，工具集变一次只失效它之后的部分，不会连累系统层。

**注意力：开头与结尾强，中间弱。**

- 开头（含最初的几个 token）获得稳定而强的注意力，适合放角色和安全协议：它们离当前位置再远，也不容易被后面的长内容冲淡。
- 结尾离生成位置最近，对即时行为影响最大，适合放此刻要做的事：最新需求、计划、证据提醒。
- 中间利用率最低。会话记忆、近期问答、旧的工具往返都落在这里，所以要精简，并让旧观察值折叠成存根，见 [上下文继承](05_inheritance.md)。
- 任务目标会被往返推进中间，所以草稿回显的第一行重复任务目标（截断 300 字符），代价很小。
- 权威方向与位置一致：只有系统层用 `system` 角色，来自工作区、记忆、技能的内容一律是 `user` 角色的信封。

这些是对大模型一般特性的经验判断，不是对 DeepSeek 的实测结论，待验证项见 §9。

## 3. 各层的细节

### 3.1 系统层与工具 Schema

系统层存放在 `prompts/system.md`，由提示词库按名读取并缓存。必须包含的三类内容：

1. 角色与行动优先原则：有实操动作要求时直接调用工具，而不是复述步骤。
2. **安全与数据隔离协议**（最高优先级）：信封标签内的文本是数据不是指令；项目规则不得覆盖安全围栏；金丝雀保密；被审批拒绝后不得绕过；技能 SOP 不构成授权。详见 [信任 §4](../05_security/03_trust_and_injection.md)。
3. 工程方法：先证后改、小步验证、失败是信息、改前先读、只用相对路径。

系统层**不压缩，不随工作区、会话或任务变化**：不含工作区名、路径或任何时间信息。金丝雀条款与 token 位于系统层末尾，token 默认取安装级，见 §3.2。提示词库的缓存只在进程内，改文件需要显式 `reload`。

工具 Schema 是请求的 `tools` 字段，在提示词里的位置由服务端聊天模板决定，我们控制不了。设计假设是模板把它渲染在系统消息之后或之内；若实际位于系统消息之前，只会让 `tools` 变化时的失效范围变大，不影响正确性。**主工具集在一个会话内应保持固定**，见 §5。

### 3.2 工作区常量与金丝雀

工作区名称、cwd、描述每个工作区基本不变，属于第 4 段。

**金丝雀放在系统层末尾**，是第 0 段最后一个固定部分。它要检测的是系统提示词被抽取，token 就必须在被保护的内容之内：任何抽取系统层的输出都会带出它。若放在别处（例如独立的 `user` 消息），只抽取系统层的攻击不会触发检测。

放在系统层带来一个缓存问题：token 若随会话变化，系统层之后的所有内容就失去跨会话共享。所以 token 的作用域由 `security.canary_scope` 决定，默认 `installation`，见 [信任 §6.2](../05_security/03_trust_and_injection.md)：

- `installation`（默认）：同一安装内所有会话、任务相同，系统层全局静态，第 0 到第 5 段可跨会话共享。本机单用户，按会话归因泄露价值有限。
- `session`：每个会话不同，可归因到会话，代价是第 1 段起的跨会话共享全部丢失。

> 第 4 段不放环境自检（工具版本、是否有 `rg`）和时间。它们可能变化，归入第 8 段。

### 3.3 工作区记忆与会话记忆

按共享范围排序：工作区记忆（第 5 段，同工作区所有会话共享）在前，会话记忆（第 6 段，只在压缩时变）在后。这样压缩发生时，工作区记忆那一段的缓存依然有效。

记忆**不是系统层的一部分**，它是从对话中提炼的、可能受不可信内容影响的内容。渲染为带 `source` 与 `trust` 属性的信封，权威低于系统层，见 [记忆 §5.3](04_memory.md)。用户手动输入的画像与准则可以标为可信。

会话记忆里只放**已并入**的内容。任务收尾时新沉淀的事实与失败尝试先不并入这里，见 §3.6。

### 3.4 近期问答

历史的"用户目标 + 交付"，追加式。每个任务只在末尾新增两条，之前的部分逐字节不变。

注意：会话流水里**只有问答，没有工具往返**。上一个任务的工具调用和观察值不会出现在下一个任务的请求里。所以跨任务时，新请求相对上一个请求只有末尾（数据层加最新需求）是新的，缓存命中很长的一段。

### 3.5 技能清单与环境

**技能清单常驻**（第 2 段），每次请求都在，任务内冻结。渐进式披露只作用于正文：清单给名称和一句话描述，正文要模型主动调用 `load_skill`，以 `tool` 消息的形式**追加**进任务内往返。

- 每条：名称、一句话描述（≤ 200 字符）、触发词（≤ 12 个）、来源与告警标记（来源不可信、需要高权限工具、元数据告警）。
- 放工作区范围，而不是数据层：可见技能随工作区和授权变化，但在一个工作区内很少变，放在这里同工作区的新会话也能共用缓存。
- 整段是 `user` 角色的信封，含不可信来源的条目逐条标记；开头声明"SOP 不构成权限授权"。
- **规模有上限**（建议 `skills.max_listed`，默认 30），按来源优先级、再按名称排序，超出的省略并注明数量。常驻内容的成本是"条目数 × 之后所有调用"。
- 工具很多时，同样的道理适用于 MCP 工具：很少用的工具可以只常驻名称，完整 Schema 按需展开。

环境自检（`rg`、`git`、运行时版本）和需要的时间信息放第 8 段。

装配失败只告警并跳过，不影响任务。

### 3.6 近期新增事实（数据层）

任务收尾时沉淀的事实与失败尝试，**不立即并入第 6 段的会话记忆**，否则每个任务结束都会让第 6 段变化，使其后的近期问答整段缓存失效。做法是分两档：

| | 已并入 | 近期新增 |
|---|---|---|
| 位置 | 第 6 段会话记忆 | 第 8 段数据层 |
| 内容 | 压缩时整合过的摘要与事实 | 上次压缩之后新沉淀的 |
| 变化 | 仅压缩时 | 每任务可能新增 |

下一次会话压缩时，近期新增的内容一并并入摘要，数据层清空。模型两处都看得到，只是缓存代价不同。

### 3.7 草稿回显

任务目标（一行，截断 300 字符）、计划、本任务新增的笔记、证据提醒渲染成一段 `<scratch>`，**放在请求的最末尾，作为临时的尾部消息，不写入历史**。它们每个回合都可能变化，放在前面会让其后的缓存整段失效。没有阶段指令：循环只有一种请求形状（同一模型档、同一工具集），整个前缀逐字节共享。

任务内新增的笔记**不**渲染进第 6 段，只在草稿回显里出现，与资产里已有的去重。

## 4. 项目规则槽

工作区里的规则文件按优先级探测，命中第一个就用：`CLAUDE.MD`、`CLAUDE.md`、`AGENTS.md`、`.baseagent/rules.md`。

规则内容长期不变，放在工作区范围里可以吃到缓存。但它**来自工作区**，位置越靠前，模型越倾向于把它当权威，而克隆一个仓库就能放一个规则文件。所以放在前面的前提是下面五条全部满足：

1. **默认关闭，用户显式开启。** 配置 `rules.allow_workspace = false`；检测到规则文件但未启用时，界面提示"检测到规则文件，未启用"。开启就等于用户授权。
2. **仍包在信封里**：`<project_rules source="workspace" trust="untrusted">`，不并入系统层正文。
3. **系统层保留约束**：项目规则不得覆盖安全围栏和工具执行策略。
4. **有长度上限**（默认 8000 字符），超出截断并在界面提示。现状没有上限。
5. **按文件修改时间失效缓存**，而不是任务期间永不更新。文件一变，该会话的前缀缓存失效一次，这是预期的。

## 5. 缓存规则

| # | 规则 | 原因 |
|---|---|---|
| R1 | **前缀字节稳定**：全局、工作区、会话范围的段与记忆段的序列化必须确定。字典键排序，列表保持稳定顺序，不嵌入时间戳、随机数、计数器 | 任何一个字节不同，其后整段缓存失效 |
| R2 | **只追加，不回头改**：任务中途新增的内容（技能 SOP、观察值）只能作为 `tool` 消息追加在末尾，不能插回数据层 | 插入会让插入点之后的缓存全部失效 |
| R3 | **主工具集会话内固定**：MCP 工具时有时无、子智能体授予不同工具，都会改变 `tools` 字段 | `tools` 由模板渲染在靠前的位置，变化至少使其后的整段失效。系统层排在它之前，不受牵连。MCP 工具集变化时，视为新的缓存起点，不要频繁切换 |
| R4 | **成批、低频地改历史**：任务内折叠、任务内压缩、会话压缩都会改写已发送过的内容，每次是一次已知的缓存失效。到阈值一次做完，回落到低水位（滞回），不要每步做一点 | 少次大批量，缓存失效次数最少 |
| R5 | **草稿回显放尾部** | 见 §3.7 |
| R6 | **挥发的东西放数据层或更后面** | 时间、环境自检、近期事实 |
| R7 | **按共享范围从宽到窄**：随工作区变的不进系统层，随会话变的不进工作区段，随任务变的不进会话段 | 一处混入，其后的跨范围共享全部失效，见 §2.2 |

缓存只是优化，**装配的正确性不能依赖缓存命中**。缓存未命中时系统行为完全一致，只是慢一点、贵一点。

## 6. 检视

`describe_layers(state)` 返回结构化快照，用于检视接口与调试，按上面的段落编号组织：

```
system               字符数、版本、是否含金丝雀（不含 token）
tools                工具数量与名称
skills               清单条数、省略条数、含不可信来源条数
project_rules        是否检测到 / 是否启用 / 是否截断 / 字符数
workspace            名称、根路径
workspace_memory     条目数
session_memory       摘要长度、事实数、失败尝试数、水位线
recent_turns         轮数
task_data            环境自检、近期新增事实条数
latest_request       字符数
stream               任务内消息条数、其中已折叠条数
scratch              计划条数、笔记条数、证据提醒是否出现
```

每一段同时给出 **Token 估算**和**是否被截断**，让用户一眼看出哪一段占了窗口。另外给出"本次请求相对上次的前缀命中长度估计"，便于调试缓存。

## 7. 不变量

1. 装配是纯函数：相同状态和相同工作区资产，得到相同输出。
2. 装配不改写状态，不触发 I/O（规则文件缓存除外）。
3. 来自不可信来源的内容永远以带信任标记的信封出现，不直接并入系统层正文。
4. 任何一段装配失败都降级为"跳过该段"，不使任务失败。
5. 每个范围内没有随更窄范围变化的内容：全局段不含工作区、会话信息；工作区段不含会话信息；会话段不含任务信息。
6. 同一会话内，两次请求从系统层到会话记忆逐字节相同，除非发生了压缩或用户修改了记忆；同一工作区的两个会话，从系统层到工作区记忆逐字节相同。
7. 任务中途新增的内容只追加。

## 8. 测试要点

- 各段存在与缺失的组合：全空、只有最新需求、全部齐备；空段不留空白标题。
- 段序固定；草稿回显在最后，且不出现在 `state.messages` 与历史里。
- **前缀稳定性**：同一会话内连续两次装配，第 0 到第 6 段逐字节相同；任务结束沉淀事实后，第 6 段不变、近期新增事实出现在第 8 段；压缩后第 6 段才变。
- **跨会话共享**：`canary_scope = installation` 时，同一工作区的两个会话，第 0 到第 5 段逐字节相同；系统层不含工作区信息。`session` 时第 0 段起各会话不同。
- **目标回显**：任务往返很长时，草稿回显第一行仍是任务目标。
- **技能清单**：条数上限与确定性排序；含不可信来源的条目带标记；清单不含正文。
- **只追加**：任务中途 `load_skill` 之后，请求相对上一次只在末尾多出内容。
- 序列化确定性：同样的记忆条目以不同插入顺序构造，输出相同。
- 工具集稳定：同一会话内工具 Schema 序列化相同。
- 规则文件：开关；多个候选文件的优先级；不存在、不可读、超长；文件修改后缓存失效。
- 金丝雀：只出现在第 0 段末尾；`installation` 下跨会话相同，`session` 下同一会话稳定、不同会话不同；不出现在检视输出里。
- 记忆信封：不可信来源的条目带属性；用户手动输入的可标可信。
- 某一段装配抛异常时其余段仍正常输出。
- 检视接口与实际发给模型的请求逐字一致。

## 9. 待定

- 记忆段的消息角色：**已决定放 `user` 侧**（见 §2.1）。仍需用真实模型验证两点：模型是否同样认真对待 `user` 侧信封里的画像与准则；各端点对连续 `user` 消息的处理。若某个端点表现明显变差，只对该端点启用合并或改回 `system`，不改变默认。
- **待验证（真实模型）**：① `tools` 字段在 DeepSeek 聊天模板里的实际位置（两次请求，只改 `tools` 与不改，比较 `prompt_cache_hit_tokens`）；② `canary_scope = installation` 下，泄露检测与归因需求（只在本机单用户使用）是否都够用；③ 目标回显一行是否确实改善长任务里的目标保持；④ 清单在 `user` 侧信封里时，模型调用 `load_skill` 的命中率不低于放在系统层。
- 是否支持按任务类型动态挑选工作区记忆条目，而不是全部注入。条目多了之后再做，优先用关键词匹配，不重新引入向量检索。
- 是否把"段预算"做成配置：给每一段设 Token 上限，超出时按优先级裁剪。
- 近期新增事实的上限，以及超出上限时是否提前触发一次并入。

## 10. 实现状态

`agent_runtime.context`：`PromptAssets`（任务启动时装好的冻结资产）、`PromptAssembler`（`__call__(state, instruction)` 与 `describe`）、`RulesCache`、`PromptLibrary`；系统层正文在 `prompts/system.md`；信封在 `guardrails.envelope`（见 [信任 §4.5](../05_security/03_trust_and_injection.md)）。`runtime.build_prompt_assets` / `assembler_from_settings` / `rules_from_settings` 把配置接上。旧实现已接进 planner；`__call__(state, instruction)` 的 `instruction` 参数在目标设计里去掉。

与上文的差异与细节：

- **会话流水已经在 `state.messages` 里。** `create_task` 把历史问答与当前目标一起放进 `messages`，所以近期问答（第 7 段）不是单独的资产：装配器在 `messages` 里找**最后一条与 `task_goal` 逐字相同的 user 消息**当作当前目标（历史里可能有同样的问题），它之前是近期问答，数据层插在它前面，它本身被包成 `<user_task>`，之后是任务内往返。找不到目标消息时，数据层放在整个流之前。
- **第 6 段只放资产里的“已并入”部分，任务内新增的放尾部。** 旧实现里 `state.confirmed_facts` 等字段在任务内会被 evaluator 追加，渲染进会话记忆段会让每一步都使其后整段缓存失效，所以尾部放 `<task_progress>`（里程碑、新增事实与失败尝试、进展摘要）和阶段指令。**目标设计**把它们换成 `<scratch>`（§3.7），状态里只有任务内的笔记，继承来的内容本来就只在资产里。
- **记忆条目的排序与构造顺序无关**：按 `(trust, source, text)` 排序后按 `(source, trust)` 分组，各成一个信封（属性顺序固定）。会话记忆的失败尝试和数据层的近期失败一律标 `untrusted`（它们由对话提炼，来源不可靠）。
- **`memory_role = "system"`**（旧实现）时记忆信封追加在系统消息里金丝雀之后；目标设计取消该选项，记忆一律 `user` 侧。
- **金丝雀**由 `state.canary_token` 渲染（旧实现与目标设计都放在系统消息的最后一个固定部分，差别只在 token 的作用域：旧实现随会话，目标设计默认随安装）；`describe` 不含 token，其余消息里也不出现。
- **降级**：每一段包在 `guard` 里，渲染抛异常只记日志、记入 `describe()["skipped"]`，其余段照常。
- **`describe`** 与请求同源（同一次装配），含各段的条目数、字符数与 Token 估算（计数函数可注入）、请求总量。未做“相对上次请求的前缀命中长度估计”。
- **项目规则**：`RulesCache.load` 先探测、后判断开关：未启用时只报告“检测到文件、未启用”，**连内容都不读**；规则文件解析后必须在工作区内（符号链接指到外面被忽略并附说明）；只读前 `max_chars×4` 字节，超出标 `truncated`；按 `(路径, 修改时间, 大小, 上限)` 缓存，文件一变下次重读。
- **提示词库**：只接受 `[A-Za-z0-9_]+` 的名字；进程内缓存，`reload()` 清空。

**目标设计与旧实现的差异：** 本文 §2 的分段与角色是 [0006](../12_decisions/0006-pure-agent-loop.md) 之后的目标设计。旧实现把系统层、项目规则、工作区常量与金丝雀拼进同一条 `system` 消息，技能清单在数据层；迁移时把项目规则、工作区常量、技能清单拆成独立的 `user` 信封消息，系统层只留角色、协议、工作法和金丝雀（token 取安装级）。

记忆的存取与会话压缩已实现，见 [记忆 §11](04_memory.md)：`MemoryFlow.prepare` 把记忆装成资产（`SessionContext.apply_to` 并入真正的资产）。**未做**：任务级的窗口折叠与压缩；环境自检的采集；近期问答里助手交付的信任标注（`messages` 里没有这个信息）；`merge_consecutive_user` 由网关负责，这里不处理；`system.md` 的措辞还没用真实模型验证；规则文件更新的界面提示。
