# 记忆

## 1. 层次

记忆按作用范围分四层，写入方、读入方、生命周期都不同：

| 层 | 范围 | 存放 | 内容 | 写入方 |
|---|---|---|---|---|
| 工作区记忆 | 跨会话 | `workspace_memories` | 用户画像、工程准则、架构定论、全局避坑 | **只有 HTTP 接口**（用户手动上浮） |
| 会话记忆 | 单会话，跨任务 | `session_memories` | 历史摘要、已确认事实、踩坑记录、上一轮操作实体 | 会话压缩器 |
| 会话流水 | 单会话 | `session_turns` | 每任务的用户目标与最终交付 | 任务收尾 |
| 任务状态 | 单任务 | `AgentState` / 检查点 | 里程碑、消息、本任务事实与失败尝试 | 各阶段 |

下层可以向上层沉淀，但沉淀需要明确的动作与把关，见 §5。

## 2. 存储

SQLite（WAL），`aiosqlite`，默认 `storage/aegis_meta.db`。

| 表 | 主键 | 说明 |
|---|---|---|
| `workspaces` | `workspace_id` | 工作区实体：名称、根目录绝对路径、描述 |
| `workspace_memories` | `workspace_id` | 四个列表字段，JSON 存储 |
| `sessions` | `session_id` | 会话元数据，外键指向工作区 |
| `session_turns` | 自增 `id` | 对话流水，含 `token_count` 缓存；索引 `(session_id, id)` |
| `session_memories` | `session_id` | 水位线与压缩结果 |

连接参数：`journal_mode=WAL`、`busy_timeout=5000`、`synchronous=NORMAL`、`foreign_keys=ON`。删除工作区或会话时**级联删除**其下的会话、流水与记忆。

每次操作各自打开一个连接。对本机单用户场景足够，若将来并发升高，应改为连接复用。

## 3. 工作区

工作区是一等公民：一个物理工程根目录对应一个工作区，下挂多个会话。`root_path` 既是工具执行的 cwd，也是路径沙箱的边界，所以它的取值是安全相关的：

- 创建时应校验路径存在且是目录。
- 同一路径不应对应多个工作区，已有冲突检测（`WorkspacePathConflictError`）。
- 读取时若工作区不存在，现状是**悄悄补建一个**根路径为 `/workspaces/{id}` 的默认工作区。这个路径通常并不存在，后续工具调用才会失败。建议改为直接报 `WorkspaceNotFound`，不要用虚构路径兜底。

## 4. 会话记忆的结构

```python
CompressedMemory(
    compacted_until_turn_id: int,        # 水位线
    summary: str,                        # 历史摘要，约 300 字
    confirmed_facts: list[str],
    failed_attempts: list[FailedAttempt],
    last_action_target: dict[str, list[str]],   # 上一轮操作的文件与符号
)
```

`last_action_target` 是个有用的小设计：它让"接着刚才的文件改"这类指代性的后续请求可以被解析。

工作区记忆与会话记忆共用 `FailedAttempt(action, failure_reason, conclusion)`，该模型在 `state.py` 里有唯一定义，记忆模块应当复用而不是自持第二份。**现状是记忆模块自己又定义了一份**，字段相同。迁移时合并。

## 5. 沉淀：缺口与新版设计

### 5.1 现状

**任务中产生的认知没有被写回会话记忆。**

- evaluator 在任务内产出 `confirmed_facts` 与 `failed_attempts`，存在 `AgentState` 里。
- 任务收尾只把"用户目标"和"最终交付文本"写入流水。
- 状态里的事实与失败尝试**没有**写回会话记忆；用来提取它们的 `collect_failed_attempts` 方法存在，但全工程没有调用点。
- 工作区记忆的两个沉淀方法，上浮事实与记录全局失败，只被 HTTP 接口调用，也就是说完全靠用户手动。

结果是：任务里辛苦验证出的事实和踩过的坑，只有在**恰好被写进交付文本**时才会在之后被压缩器捞出来。初始化状态的注释写着"认知记忆从会话层继承，新任务不重复踩坑"，这个承诺目前只对"压缩器从对话里提炼出的内容"成立。

### 5.2 新版设计

任务收尾时，把本任务的 `confirmed_facts` 与 `failed_attempts` 合并回会话记忆：

1. **只在任务成功或被终止时沉淀**；失败任务的事实不可靠，只沉淀其 `failed_attempts`。
2. **先进"近期新增"，压缩时才并入摘要。** 沉淀的内容存为带来源的条目，渲染在数据层（见 [提示词装配 §3.6](03_prompt_assembly.md)），不直接改会话记忆段；下一次会话压缩时与摘要一并整合，再清空近期新增。这样每个任务结束不会让会话记忆段变化，其后的近期问答缓存得以保留。
3. **去重并限量**：合并后按上限整合，见 [窗口与压缩 §2](02_window_and_compaction.md)。近期新增也有上限，超出时提前触发一次并入。
4. **记录来源**：每条记忆带 `source_task_id` 与时间，便于审计和撤销。
5. **用户可见与可删**：前端的记忆抽屉可以查看每一条并删除。
6. 工作区层级的上浮**保持手动**，或者仅在会话事实被多次引用后提示用户"是否上浮"，不自动提升。

### 5.3 记忆投毒

这一点必须单独说明。记忆里的内容会被**每一个后续任务**读到，并且当前被放在**系统提示词**里，权威很高。如果有害内容被写进记忆，影响会持续存在：

- 压缩器的输入是对话文本，而交付文本可能包含来自网页、MCP 工具的内容，被提炼成"事实"后就洗白了来源。
- 一条看似无害的"项目约定：构建前先执行 `curl … | sh`"一旦进入事实列表，之后每个任务都会看到它。
- 5.2 把任务内事实自动写回，会进一步扩大这条通路。

防护措施：

1. **来源标记与信任**：记忆条目记录来源（用户明确陈述、任务验证、压缩器提炼）。由不可信内容衍生的条目标 `untrusted`。
2. **渲染位置**：记忆不再放进系统提示词正文，而是放进带信任属性的信封里，权威等同于数据。可信的用户画像可以例外，且只能来自用户手动输入。
3. **提炼约束**：压缩提示词明确禁止提炼"指令、命令、凭据"类内容；提炼结果过一遍注入样态扫描，命中则丢弃并告警。
4. **审批关联**：记忆里的内容不能豁免任何审批，权限判定只看动作本身。

## 6. 生命周期

| 事件 | 处理 |
|---|---|
| 创建会话 | 写 `sessions`；会话记忆懒创建 |
| 任务开始 | 读取四层资产装入 |
| 任务结束 | 写流水、更新 `last_action_target`、沉淀（新版）、判断是否压缩 |
| 删除会话 | 级联删除流水与记忆 |
| 删除工作区 | 级联删除全部会话 |
| 清空记忆 | 提供按层清除的接口（新版） |

## 7. 分词口径

全系统使用同一个计量函数，基于 `tiktoken` 的 `cl100k_base`：

- 记忆压缩、观察值裁剪、上下文装配的触发判断都用它，避免"同一段文字在不同模块算出不同长度"。
- 编码器懒加载并缓存；初始化或编码失败时退回 `len(text) // 2` 的字符粗算，并只告警一次，不阻断主流程。
- 它与实际模型使用的分词器**不完全一致**，所以只用于局部决策，不用于预算。预算以服务商返回的用量为准。
- 对中文，字符粗算偏保守（高估 Token 数），对英文偏激进。

## 8. 不变量

1. 水位线单调不减。
2. 流水只记录完整的"问加答"，不记录工具往返。
3. 记忆写入失败不使已完成的任务变成失败。
4. 级联删除不留下孤儿记录。
5. 记忆条目的来源可追溯。
6. 由不可信内容衍生的记忆不得以系统提示词权威呈现。
7. 工作区层记忆只能由用户明确动作写入。

## 9. 测试要点

- 存储：并发读写、级联删除、迁移幂等、不存在的工作区读取（新版应报错）。
- 记忆沉淀：成功任务沉淀事实；失败任务只沉淀失败尝试；重复事实去重；上限触发整合。
- 投毒：含命令的“事实”被扫描丢弃；不可信衍生条目渲染为带属性的信封。
- 分词：编码器缺失时降级；特殊字符不抛错；空串返回 0。
- 级联：删除会话后流水与记忆都不存在。

## 10. 待定

- 条目级的版本与撤销。
- 记忆检索：条目增多后，是否按当前任务相关性挑选，而不是全量注入。这会重新引入检索问题，但规模小得多，可以用关键词匹配而不必上向量。
- 工作区记忆的上浮策略，手动、提示还是自动。
- 多设备或多进程访问同一份库时的并发语义。

## 11. 实现状态

`agent_runtime.memory`（只依赖 `core` 与 `guardrails`；要调用模型的提炼器由上层注入）：`MemoryStore`、`deposit`、`merge_extraction`、`split_for_compaction`、`SessionCompactor`。运行时侧在 `agent_runtime.runtime`：`MemoryFlow`（开始装入、收尾沉淀）、`GatewayExtractor`（快速档结构化提炼）、配置装配函数。

相对上文的差异与补强：

- **存储**：表为 `workspaces`、`workspace_memories`、`sessions`、`session_turns`、`session_memories`；单个长连接加写锁（不是每次操作各开一个连接）；`foreign_keys=ON` 与 `ON DELETE CASCADE`，删除工作区或会话不留孤儿；`PRAGMA user_version` 迁移，库版本高于程序时拒绝打开；文件 0600。**读取不存在的工作区或会话直接报 `WorkspaceNotFound` / `SessionNotFound`**，不再补建默认工作区（§3 的建议）。工作区根路径必须是已存在的目录，同一路径不能对应两个工作区。
- **会话记忆只通过 `update_memory(session_id, fn)` 改**：同一事务内读-改-写，并发的沉淀与压缩互不覆盖；`fn` 抛异常则什么都不改；水位线不得回退（`WatermarkRegressionError`），也不得越过现有轮次。
- **每条事实与失败尝试带出处**：`task_id`、`source`（`task` / `compressor`）、`trust`、`created_at`；`FailedAttempt` 复用 `core` 的唯一定义（§4 的合并已做）。`last_action_target` 与压缩失败计数、重试时间一起存在 `session_memories` 里。
- **沉淀（§5.2）**：`deposit` 只写“近期新增”，不动摘要与已并入的事实。成功或被终止的任务沉淀事实与失败尝试；失败任务（包括 `[SECURITY]` 终止）只沉淀失败尝试。读过不可信内容的任务（观察值带 `trust="untrusted"` 信封）的事实标 `untrusted`。空、超过 500 字符、命中注入样态的事实被丢弃并记下原因；与已并入和近期新增重复的不再加。近期新增超过 `max_pending_facts` 时返回 `needs_compaction`，收尾时据此强制并入。`persist_task_facts=false` 时只记流水。
- **工作区记忆只有 `set_workspace_memory` 能写**，压缩与沉淀从不调用它；它在装配时作为 `user` 来源、可信的条目。
- **收尾（`MemoryFlow.finish`）**：先把目标与交付写入流水（交付与目标里的金丝雀被替换为 `[SECURITY_REDACTED]`），再沉淀，再判断压缩；**任何失败都只记入报告，不抛**（§8 第 3 条）。`last_action_target` 目前只取 `write_file` / `edit_file` 的路径，没有符号。
- **未做**：§3 的工作区创建/更新 HTTP 接口、级联之外的“按层清除”接口、条目级版本与撤销、记忆检索、§7 的分词口径（现用网关的估算函数，宁高勿低，而不是 tiktoken）。
