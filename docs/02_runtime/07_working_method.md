# 工作方式：确认、规划、逐个子任务推进，每一步都汇报

主循环不设阶段、不设路由（[0006](../12_decisions/0006-pure-agent-loop.md)），"先做什么、后做什么"完全由提示词引导。本文记录内置系统提示词（`prompts/system.md`）要求的工作方式，以及界面如何把它呈现出来。安全协议不在这里改动，仍在系统提示词的最高优先级一节。

## 1. 流程

1. **先确认需求。** 目标、范围、验收标准、约束。靠读代码、看环境能查明的自己查；只有关键点含糊、查不出来、猜错代价大时才提问：一次问全（不超过 3 个），给出默认假设，让用户一句话确认。提问是不带工具调用的回复，它结束本轮任务，用户答复后作为新任务继续（会话记忆保留上下文）。
2. **先判断要不要规划。** 一两步的事（回答、读文件、改一行）直接做；多步或有风险的任务用 `update_plan` 拆成 2–7 个子任务，每个有完成标准，按依赖排序，当前这个标 `in_progress`。
3. **一个子任务做完再推进下一个。** 子任务内部走完整的小循环：规划（看哪些文件、怎么做、做到什么算完）→ 确认（用本地证据确认现状）→ 执行（小步）→ 评估（测试或命令对照完成标准）。没达标就在本子任务内修，不带着问题推进。完成后 `update_plan` 标 `completed`，把下一个标 `in_progress`。计划有误先说明原因再调整。
4. **每一步都汇报**（§2）。
5. **交付**：不带工具调用的最终回复：做了什么、依据、没做或没验证的。

## 2. 汇报格式

每次调用工具之前，先写 1–3 句简短的话：

```
已完成：刚做完了什么（一句话；第一次写“现状：……”）。下一步：接下来要做什么，为什么。
进度：当前子任务名 约 N%
```

`N` 是模型对**当前子任务**完成程度的估计：0–100 的整数，随推进只增不减，子任务完成时写 100。同一批并行的工具调用只汇报一次；不复述工具参数，不写大段思考。进度是估计，不是精确值，界面不把它当作任务总进度。

## 3. 界面

- 带工具调用的 `model.reply.content` 在执行过程时间线里是一条**说明行**（`kind: 'say'`），不是灰色的事件名。没有工具调用的 `model.reply` 是最终交付，由 `task.finished` 给出，不重复显示。
- 说明行里的 `进度：<子任务名> 约 N%` 被解析成一条细进度条加百分比（`parseSay`）；格式不符就原样当正文，不显示进度条。
- 内部记账事件（`llm.call`、`turn.finished`、`plan.updated`）与旧的阶段行（`node.finished`）不进时间线，只推进事件序号。
- 事件契约见 [02_events_contract](../09_api/02_events_contract.md)；`reasoning`（若有）仍只在事件里，不渲染。

## 4. 与其他机制的关系

- `update_plan` / `note` 仍是草稿，不影响任务何时结束（[05](05_plan_and_scratch.md)）；`<scratch>` 回显保证长任务里计划与目标不丢。
- 汇报不改变权限与审批：说“下一步要执行 X”不等于获得授权，需要审批的调用照常挂起。
- 用户可以在设置里替换整段系统提示词（[视觉设计 §5](../10_frontend/03_visual_design.md)）；替换后这套流程随之失效，安全协议需要自己保留。
