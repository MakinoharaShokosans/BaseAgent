# 工具执行

`ctx.tools.run(calls)` 是循环里唯一执行工具的地方（[主循环 §2](02_main_loop.md)）。它不调用模型，输入一批调用，输出与调用一一对应的 `tool` 消息，期间完成权限、审批、拦截与后处理。

## 1. 执行顺序（固定）

1. **校验调用。** 先解析代理：`mcp_call(name, arguments)` 解析为对目标工具的调用，此后权限、指纹、幂等、信封、超时都按目标工具处理，`mcp_call` 自身不参与判定；解析失败（目标不在索引内、目标是 `pinned`、本任务未 `mcp_describe`、`arguments` 不是对象）直接合成失败结果，见 [MCP §5.1](../04_tools/04_mcp.md)。transcript 里保留模型原始发出的代理调用，崩溃补齐时同样按目标工具的幂等声明处理。不存在的工具名、参数无法使用的调用（网关登记为格式错误或被长度截断，参数形态为 `{"_raw": 原文}`）直接合成失败结果，**不参与权限判定**：它们不会被执行，不值得为幻觉出来的工具打扰人。
2. **权限闸门。** 逐个调用做 `check_permission`（纯函数）。越级且签名不在会话白名单的构成"越级集合"：
   - 无决策：抛 `ApprovalRequired`。此前**没有执行、没有提交、没有任何副作用**。
   - 有决策：先 `check_binding`，越级集合必须与请求的 `call_ids` 吻合且 `approval_id` 能由当前状态重新算出，否则报错、不套用。批准则本批越级调用可执行，`always` 把签名加入白名单；拒绝则只为越级调用合成失败结果，其余照常执行。
   - 没有越级调用时，残留的审批字段是过期的，一律清掉，不授予任何东西。

   协议细节见 [人工审批](04_approval.md)。
3. **指纹登记与拦截。** 本批所有调用的指纹追加到滑动窗口。最近 `identical_fingerprint_limit` 次完全一致、或在两个取值间来回交替（`alternation_cycles` 个周期）即命中，**整批**拦截不派发，结果写明原因。每次拦截 `consecutive_blocks` 加一，任一批正常派发则清零；达到 `max_consecutive_blocks` 抛 `LoopAborted`。
4. **派发。** 被拒绝、被拦截、参数无法使用的调用不派发。其余调用：**只读工具并发，其余按调用顺序串行**，避免同一批内两个写操作互相踩踏。每个调用独立硬超时。
5. **后处理。** 每个调用一条 `tool` 消息，顺序与调用一致。
   - 观察值裁剪与落盘（[观察值治理](../03_context/01_observation_governance.md)）。
   - 不可信工具的结果在**裁剪之后**包信封，警示语不会被截掉；可信的不包。
   - 登记产物进 `state.artifacts`，被截断时在观察值末尾追加 `[完整输出: artifact://…]`。
   - 更新 `verification`（[计划与草稿 §5](05_plan_and_scratch.md)）。
6. **连续错误通知。** 成功清零、失败按批内失败个数累加；达到阈值时在工具消息**之后**追加一条 `user` 角色的 `[系统护栏]` 通知：`已连续 N 次工具调用失败，请换一种做法；如果确实无法完成，说明受阻原因并结束。`（`system` 只能出现在最前面。）它只是通知，不改变控制流。

增量只涉及 `messages`、`consecutive_errors`、`fingerprint_history`、`consecutive_blocks`、`artifacts`、`verification`，以及消费决策时清空 `pending_approval` 与 `approval_decision`。

## 2. 什么算失败

| 情形 | 计入连续错误 |
|---|---|
| 工具 `ok = false`、退出码非零、超时、抛异常、未知工具 | 是 |
| 被指纹拦截 | 是 |
| 参数无法使用（格式错误或被截断） | 是，这是模型的错 |
| **人工拒绝审批** | **否**：不是工具失败，算进去会在用户拒绝几次后触发"工具一直失败"的通知，误导模型 |

`ToolResult.failed`：`ok` 为假，或退出码非零（即使工具自称成功）。

## 3. 拒绝与拦截的结果文案

模型只能通过工具结果得知被拒绝或被拦截，所以文案承担引导作用：

- 人工拒绝：`已被人工审核拒绝：<原因>。不要换着花样绕过这个操作，也不要编造缺失的信息；改用合规方案，或说明受阻原因并结束。`没有原因时用"用户未批准该操作"。
- 指纹拦截：`该调用与最近的调用重复，已拦截。请换一种做法，或说明受阻原因并结束。`
- 权限不足且无法请求审批（子智能体内）：`权限不足：需要 <级别>。`

## 4. 取消与崩溃

取消和崩溃恢复见 [主循环 §6、§7](02_main_loop.md)：取消时为未完成的调用补"已取消"结果；崩溃后尾部未配对的调用按幂等声明重试或合成"结果未知"。工具层只需要正确声明 `idempotent`。

## 5. 工具层（`tools.core`）与协议（`agent_runtime.core`）

- 协议在 `core`：`AgentTool`（`name`、`description`、`parameters`、`timeout_sec`、`trust`、`idempotent`、`invoke`）、`ToolResult`（冻结的 pydantic 模型，`failure()` 与 `failed`）。
- `ToolRegistry`：构造期校验空名、重名（不覆盖）、不可信工具（默认拒绝；`allow_untrusted` 时若给了逐名清单，清单外也拒绝）。`schemas()` **按名称排序**，保证请求前缀稳定。MCP 工具与技能工具经同一注册表并入，见 [MCP](../04_tools/04_mcp.md)、[Skills](../04_tools/05_skills.md)。
- `ToolDispatcher`：返回顺序与输入一致；每个调用独立硬超时；超时、异常、未知工具都变成失败结果；信任级 = 结果的调用期覆盖 > 工具的静态声明 > 未知工具取 `untrusted`；`CancelledError` 不吞。
- 子智能体是一个内部再跑一次 `run` 的工具，不请求审批、不拥有独立额度，见 [06_subagents](../06_subagents/)。

## 6. 护栏模块

| 模块 | 内容 |
|---|---|
| `guardrails.permissions` | `PermissionPolicy`（配置快照）、`check_permission`（纯函数）、`action_signature` |
| `guardrails.loops` | `compute_fingerprint`、`register_fingerprints`、`is_fingerprint_loop`、`update_consecutive_errors`、`LoopLimits` |
| `context.observation` | `ObservationLimits`、`ObservationGovernor`、`ObservationStore` |

- 签名与指纹用 sha256，长度不变。
- 非法的权限正则被跳过并记录，不影响其余规则；已知防不住的命令（解释器间接执行、脚本、`eval`）有测试固定"当前被判为只读"，防止被误当作已覆盖。
- 观察值：行数不超过 `head + tail` 但每行巨长的输出（如 base64）按长度再封顶每行（至少 80 字符）；句柄同一步内重名加 `_2`、`_3`；工具名与任务 id 净化后才进文件路径；落盘失败只留摘要。

## 7. 不变量

1. 权限判定先于任何派发；挂起前无副作用。
2. 每个调用恰好一条结果，顺序一致。
3. 工具异常不逃出 `tools.run`。
4. 同一批内写操作不并发。
5. 信封包在裁剪之后。
6. 人工拒绝不计入连续错误。
7. 代理调用的判定对象恒为目标工具。

## 8. 测试要点

- 六种路径（成功、失败、拒绝、拦截、超时、取消）都产生配对结果。
- 越级无决策 → 抛出且无副作用；决策与调用不吻合 → 报错不套用；批准 `always` 后同签名免审。
- 拦截：连续相同、ABAB 摆动、整批拦截；连续拦截达上限抛 `LoopAborted`；正常派发清零。
- 同批读并发、写串行（用带时间戳的假工具断言）。
- 参数 `_raw` 的调用不参与权限判定。
- 不可信结果先裁剪后包信封。
- `mcp_call` 的五种解析结果：成功、目标未知、目标是 `pinned`、未取过 Schema、参数非对象；越级时审批卡片显示目标名；指纹按目标名与参数计算。

## 9. 实现状态

**设计已定，代码未迁移。** 旧 `loop/stages/tool_runner.py` 已实现上述大部分逻辑（权限闸门、指纹、观察值治理、信封钩子、产物登记），迁移时拆为"包装层"与"后处理"两部分；以下是旧实现里已有而本设计沿用的**未做项**，仍然未做：

- **信封实现**（[信任 §4](../05_security/03_trust_and_injection.md)）：`envelope` 钩子已在，真实的信封函数没做；目前注册表默认拒绝不可信工具，所以尚无不可信观察值可包。
- **注入扫描**与**轨迹记录**（审批决定、拦截、通知现在只发 `guard.*` 事件）。
- 工具参数的 JSON Schema 校验（[工具系统 §14](../04_tools/01_tool_system.md)）。
- 审批的 `check_binding` 只绑定 call id 与消息位置，**不绑定参数**：状态里的 `tool_calls` 不会被重新生成，所以正常路径下被批准的就是被执行的；但检查点库被篡改时，同一 id 换参数会沿用旧批准。是否把参数哈希也纳入 `approval_id`，待定。

**新增、旧代码没有的**：同批读并发写串行、`consecutive_blocks` 与 `LoopAborted`。
