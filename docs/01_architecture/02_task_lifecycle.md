# 任务的端到端生命周期

把各子系统串起来，跟随一个任务从提交到交付，说明每一步由谁负责、写了什么、出错怎么办。

## 1. 全景时序

```mermaid
sequenceDiagram
    participant U as 浏览器
    participant A as API
    participant R as 任务注册表
    participant L as 主循环
    participant G as LLM 网关
    participant T as 工具层
    participant S as bash_shell
    participant K as 检查点库

    U->>A: POST /sessions/{id}/tasks
    A->>R: submit（并发闸门、分配 task_id）
    A-->>U: 202 + 任务快照
    U->>A: GET /tasks/{id}/stream
    R->>L: 后台协程启动
    L->>L: prepare：装入记忆，构造初始状态，装配任务级对象
    loop 每个回合
        L->>G: 调模型
        G-->>L: 响应（含用量）
        L->>K: 提交检查点（派发前）
        L->>T: 工具执行：权限判定、派发
        T->>S: bash 命令
        S-->>T: 蒸馏后的输出
        L->>K: 提交检查点（回合结束）
        L-->>R: 发事件
        R-->>U: SSE
    end
    alt 越级操作
        L->>K: 提交（pending_approval）
        L-->>U: task.waiting_for_approval
        U->>A: POST /tasks/{id}/approve
        A->>L: resume（决策）
    end
    L->>L: 收尾：回写记忆，必要时压缩
    L-->>U: task.finished
```

## 2. 分步详解

### 2.1 提交

| 步骤 | 负责 | 要点 |
|---|---|---|
| 校验请求 | API | 会话存在，字段合法，目标长度上限 |
| 并发闸门 | 任务注册表 | 超过 `max_concurrent_tasks` 返回 429 |
| 分配 `task_id` | 任务注册表 | 先返回给客户端，客户端可立即订阅事件 |
| 权限基线 | API 与注册表 | 取请求值或会话配置；`full_permissions` 需显式确认 |

### 2.2 准备（Spawn）

每个任务**重建**任务级对象，因为它们的生命周期绑定单次任务：

```
记忆装入        工作区记忆、会话记忆、活跃对话轮次
初始状态        草稿为空，金丝雀 token 取本机密钥派生（默认安装级），任务目标作为最新的用户消息
观察值裁剪器    绑定产物目录
轨迹记录器      绑定 task_id
事件总线        之后绑定本轮的回调
工具注册表      内置工具 + 研究入口 + 动态委派 + 已授权的 MCP 工具
上下文装配器    分层提示词的静态视界（冻结资产）
```

装配失败的部分降级，不拖垮任务：MCP 发现失败则跳过全部 MCP 工具；技能扫描失败则无技能清单。

### 2.3 主循环

见 [主循环](../02_runtime/02_main_loop.md)。简述：

```
调模型 ──► 有工具调用？ ──是──► 执行工具 ──► 追加结果 ──┐
   ▲                │否                          │
   │                ▼                            │
   │              结束                           │
   └─────────────────────────────────────────────┘
```

一个回合内**两次提交检查点**：模型回复带工具调用时（派发前）、工具结果追加后；每次先提交，再发事件。

一次工具执行的内部顺序：校验调用；权限判定、必要时挂起；指纹拦截；派发（只读并发、其余串行）；观察值裁剪与信封；错误计数与验证状态。见 [工具执行](../02_runtime/06_tool_execution.md)。

### 2.4 挂起与恢复

越级操作使任务**落盘挂起并释放资源**，而不是在内存里等待。恢复由审批请求触发，从检查点重新进入同一批调用，重新做同一次纯判定后消费决策。详见 [审批](../02_runtime/04_approval.md)。

### 2.4.1 任务运行器（已落地于 `agent_runtime.runtime`）

`TaskRunner` 是“任务注册表”中与运行相关的部分（HTTP 层的缓冲、事件表另算）：

- **提交** `submit(request)`：名额满则 `TaskQueueFullError`（对外 429 `TASK_QUEUE_FULL`），不登记、不落盘；否则分配 `task_id`、校验请求、**提交初始检查点**，再转入后台运行，立即返回。登记与名额检查之间没有 `await`，并发提交不会抢占同一个名额。
- **并发名额只统计 `running`**：挂起等待审批的任务释放名额；对它 `resume` 时需要空闲名额，没有则 `TaskQueueFullError`，任务保持原状。
- **续跑** `resume(task_id, decision)`：校验错误（缺决策、`approval_id` 不符、格式错误、已在运行）**同步抛给调用方**，任务原样不动；通过后转入后台。
- **状态映射**：`run` 以 `ApprovalRequired` 退出 → `waiting_for_approval`（非终态，不发 finished）；正常返回 → `succeeded`；`CanaryLeak` → `terminated`（安全终止）；其他任何异常（含模型错误、余额不足、`LoopAborted`）→ `failed`（原因 `异常类型: 消息`，状态停在上一次提交点，可续跑）；用户取消 → `cancelled`。
- **取消** `cancel(task_id)`：运行中的任务被中断，挂起的任务作废其请求；两种都把“用户取消”的终态**落盘**（`status = 'finished'`），补齐未配对的工具调用（“已取消”），清掉待审批请求与决策。所以重启后它既不会被当成“进程中断”，也不会被当成“等待审批”。已结束的任务返回 `False`。
- **关停** `shutdown()`：停止运行中的任务，但**不写终态**，状态停在上一次提交点，下次启动可续跑。
- **启动接管** `adopt(RecoveryReport)`：中断的任务记为 `failed`（原因“进程中断”，不自动续跑），挂起的恢复为 `waiting_for_approval`。
- **收尾**：`TaskObserver.task_finished` 在状态定下之后调用，出错只记日志，不改变任务结果。
- **配置装配** `max_concurrent_tasks`、`resolve_permission_level`（旧实现的 `budget_limits_from_settings` 随预算取消）：权限基线取请求值或 `runtime.approval.default_level`；`full_permissions` 需要显式确认（`require_full_permissions_confirm` 可关），基线被配成 `full_permissions` 时同样不能绕过确认。

已知局限：任务状态目前只在进程内存里。目标设计中取消落盘为 `finished`，`resume` 拒绝；持久化的任务元数据表（`GET /sessions/{id}/tasks` 需要它）留给 API 层。

### 2.5 终止

| 终态 | 触发 |
|---|---|
| `succeeded` | 模型不再调用工具，给出最终回复 |
| `terminated` | 金丝雀泄露（安全终止），不可续跑 |
| `failed` | 不可恢复异常（全部模型端点不可用、余额不足、连续拦截达上限等） |
| `cancelled` | 用户取消 |

`failed` 可续跑；`terminated`、`cancelled`、`succeeded` 不可。

### 2.6 收尾（Teardown）

非挂起的终态都会：

1. 取出面向用户的交付（最后一条助手消息；`failed` / `terminated` 时由代码生成部分交付），**脱敏金丝雀**；
2. 写会话流水（用户目标加交付），更新 `last_action_target`；
3. 沉淀本任务的事实与失败尝试到会话记忆（新版），见 [记忆 §5](../03_context/04_memory.md)；
4. 判断是否触发会话压缩（新版改为异步）；
5. 写 `final` 轨迹记录；
6. 关闭 sidecar 客户端；
7. 发 `task.finished`，关闭事件流。

收尾中任何一步失败都**不使已完成的任务变成失败**，只记录错误。

## 3. 数据在各处的形态

同一件事在不同位置有不同形态，各有各的生命周期：

| 信息 | 状态 | 检查点 | 轨迹 | 事件 | 会话记忆 |
|---|---|---|---|---|---|
| 用户目标 | `task_goal`、首条用户消息 | 是 | `final` | `task.started` | 流水 |
| 工具调用与结果 | `messages` | 是 | `tool`，含入参 | `tool.call` / `tool.result` | 否 |
| 被裁剪的完整输出 | `artifacts` 句柄 | 句柄 | 句柄 | 句柄 | 否 |
| 模型思考内容 | 助手消息的 `reasoning` | 近期部分 | 截断摘要 | 截断摘要 | 否 |
| 最终交付 | 最后助手消息 | 是 | `final` | `task.finished` | 流水 |
| 本任务笔记（事实、失败尝试） | `facts`、`failed_attempts` | 是 | — | — | 沉淀后进入 |
| 计划 | `plan` | 是 | — | `plan.updated` | 否 |
| 网页正文 | **不存在**（隔离区内用完即弃） | 否 | 否 | 否 | 否 |

## 4. 失败路径速查

| 失败 | 发生位置 | 处理 | 任务结果 |
|---|---|---|---|
| 模型端点全部不可用 | 网关 | 降级链耗尽，抛异常 | `failed`，原因"LLM 不可用"，可续跑 |
| 余额不足 / 鉴权失败 | 网关 | 作为不可恢复的模型错误抛出 | `failed`，充值后可续跑 |
| 单次调用超过总耗时上限 | 网关 | 放弃该调用 | `failed`，可续跑 |
| 工具业务失败 | 工具层 | 失败观察值回给模型 | 继续，计入连续错误 |
| 连续错误达阈值 | 工具包装层 | 在工具结果后追加通知 | 继续 |
| 参数重复 / 摆动 | 工具包装层 | 整批拦截；连续拦截达上限抛 `LoopAborted` | 继续，或 `failed` |
| 越级操作 | 工具包装层 | 挂起 | `waiting_for_approval` |
| 审批被拒绝 | 工具包装层 | 合成拒绝结果 | 继续，要求改用合规方案 |
| 金丝雀泄露 | 网关 | 抛 `CanaryLeak`，不返回该响应，其中的工具不执行 | `terminated` |
| sidecar 不可达 | 工具层 | 失败观察值 | 继续 |
| 进程崩溃 | 任意 | 重启后扫描检查点 | 标记失败，等待用户续跑 |
| 检查点写入失败 | 主循环 | 视为任务失败，不带着未持久化的进度继续 | `failed` |
| 事件、轨迹、追踪写入失败 | 旁路 | 只告警 | 不影响 |

## 5. 并发模型

- 默认同一时刻一个任务（`max_concurrent_tasks = 1`），串行化资源。
- 任务内：同一批工具调用中只读并发、其余串行；子智能体在工具执行内部运行；网关对每个端点有并发上限。
- 全部是单个事件循环内的协程。
- 阻塞 I/O（文件、分词、正文提取）进线程池，不阻塞事件循环。
- 取消通过 `asyncio` 取消传播，各处的清理放在 `finally` 且不含可被取消的 `await`。

## 6. 一致性边界

| 一致性问题 | 保证 |
|---|---|
| 状态与检查点 | 每个回合两次提交；崩溃后从最近提交点继续，尾部未配对调用按规则补齐 |
| 事件与检查点 | 先提交，后发事件 |
| 工具副作用与检查点 | 派发前提交；崩溃后对可能已执行的非幂等调用合成"结果未知"，不盲目重放 |
| 记忆与任务结果 | 任务结果优先，记忆回写失败不影响结果 |

## 7. 待定

- 多任务并发（`max_concurrent_tasks > 1`）下，对同一工作区的并发写入如何协调。目前不支持，并发上限默认 1。
- 任务之间的依赖（`parent_task_id` 已有字段但未被运行时使用）。
