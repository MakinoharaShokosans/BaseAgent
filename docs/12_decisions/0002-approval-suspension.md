# 0002 审批采用落盘挂起

- 状态：**已采纳**
- 影响：[02_runtime/04_approval.md](../02_runtime/04_approval.md)、[02_runtime/03_checkpoint_and_resume.md](../02_runtime/03_checkpoint_and_resume.md)

## 背景

越级操作需要人工审批，运行时必须能在等待期间暂停任务，并在决策到达后继续。

## 选项

**A. 进程内等待。** 阶段函数 `await` 一个 `asyncio.Future`，决策到达时 resolve。

- 实现最简单，不需要重新进入阶段。
- 等待期间一直占用并发名额和协程。
- 进程重启即丢失挂起状态，用户已经看到的审批卡片会失效。
- 挂钟计时仍在走，容易因为用户离开一会儿就耗尽时间预算。

**B. 落盘挂起。** 阶段抛出 `ApprovalRequired`，循环提交带 `pending_approval` 的检查点并退出；决策到达后由 `resume` 重新拉起，重新进入同一阶段。

- 等待不占资源，进程重启不丢失，挂钟不累加。
- 要求阶段在抛出前无外部副作用，并且重新进入后的判定必须是确定性的。
- 需要设计决策与请求的绑定，防止错配与重复提交。

## 决定

选 B。它与"可恢复"这一设计取向一致，且与旧版行为（`interrupt` 加 `Command(resume)`）对外语义相同，前端与 API 无需改变协议。

## 后果

- `tool_runner` 必须把权限判定放在阶段开头，并保持判定为纯函数。
- `approval_id` 改为确定性生成，使重新进入时请求保持一致。
- 状态增加 `pending_approval` 与 `approval_decision` 两个控制字段。
- 子智能体不得请求审批，越级一律以失败回给父级。
- 白名单不入检查点，进程重启后会重新询问。
