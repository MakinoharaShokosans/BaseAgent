# 0004 追踪采用内部 span 模型加可插拔导出，移除 LangChain 回调式集成

- 状态：**已采纳**
- 影响：[08_observability/03_tracing.md](../08_observability/03_tracing.md)、`pyproject.toml` 依赖

## 背景

去掉 LangGraph 与 LangChain 后，原先设计里"把 Langfuse 回调挂到图执行上"的外部追踪方式失效。核对代码发现，这个集成从未被调用过，是未接入的死代码，依赖却在默认依赖里。

## 选项

**A. 自有轻量 span 模型，本地 JSONL 为主，导出器可插拔（OTLP、Langfuse 可选）。**
- 核心不依赖任何第三方追踪库。
- 同一棵调用树可以导出到多个后端。
- 代价：要自己实现 span 上下文与导出队列，代码量不大。

**B. 直接采用 OpenTelemetry SDK 作为内部实现。**
- 生态和语义约定现成。
- 核心默认依赖变重，SDK 的异步上下文与我们的事件循环模型需要适配。

**C. 只保留 Langfuse，在网关与工具派发处手动打点。**
- 实现快。
- 与单个厂商的 SDK 绑定，大版本变更时需要跟随；本地没有该服务就没有调用树。

## 决定

选 A。内部 span 模型简单、与事件和轨迹的关联键天然一致；导出器接口很窄，OTLP 导出器可以覆盖大部分后端，包括 Langfuse 的 OTLP 入口。

## 后果

- 轨迹、事件信封、日志上下文都增加 `span_id` 与 `parent_span_id`。
- `langfuse` 移出默认依赖，进入可选依赖组。
- 远程导出与内容导出默认关闭，开启要显式配置并在界面提示。
- 挂起等待审批的时间在追踪里归为独立的 `guard:approval` span。
- 若将来改为 B，导出器接口与 span 模型可以直接映射，迁移成本低。
